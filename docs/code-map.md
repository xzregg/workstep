# 按功能查找代码

流程触发与通知钩子的服务错误由 `apps/daemon/services/hook_errors.py::HookError` 表达，HTTP 状态映射仅在 `api/hook_errors.py::invoke_hook` 执行。服务层不依赖 FastAPI／Starlette；错误码、异常保留及分层回归入口为 `tests/test_hook_errors.py`、`test_backend_layering.py` 和两类钩子的 API 行为测试。

通知钩子入口为「流程钩子」→「通知钩子」。`WorkflowHookManagerDialog` 只组装类型选择，`WorkflowHookTypeTabs` 复用导航，`NotificationHooksDialog` 自管理多目标配置、预览、测试、投递记录与未保存保护；API 客户端为 `api/notificationHooks.ts`。设备 `api/notification_hooks.py` 和 `schemas/notification_hooks.py` 持有管理接口与校验，`services/notification_hooks.py` 持有异步事件采集及持久化后台投递，`notification_delivery.py` 持有平台格式、加签、超时及脱敏错误；模型为 `models/notification_hook.py`。任务轮次事件由 `workflow_runtime.py` 与人工审核 `review_decision.py` 持有，步骤复用 AG-UI 状态及交互事件。网关仅通过共享协议 `project_scope.py` 开放项目编辑路由。行为测试为 daemon `test_notification_hooks.py`／`test_workflow_runtime.py`／`test_review_gate.py`、Web `notificationHooks.test.tsx`、协议 `test_hooks.py`；技术说明见 [通知钩子](notification-hooks.md)。


流程钩子入口为任务列表工具栏／移动菜单 → `WorkflowHooksDialog.tsx`，自管理多钩子配置、模拟、保存和关闭保护；`api/workflowHooks.ts` 生成统一三类地址。设备管理与公网入口归 `api/workflow_hooks.py`，持久化和索引归 `services/workflow_hooks.py`／`models/workflow_hook.py`，复用 `create_project_task`。网关 `api/workflow_hooks.py` → `services/workflow_hooks.py` 按已签名登记的 `devices.hook_device_id` 找到设备，使用 `DataConnection.proxy_http(hook_request=True)` 和设备 `ManagedHttpBridge` 转发固定 POST 路径，不保存钩子数据；安装标识签名登记由两端控制连接握手持有。共享协议 `hooks.py` 持有入口边界与日志脱敏，`project_scope.py` 限定钩子管理为项目编辑。行为测试为两端 `test_workflow_hooks.py`、Web `workflowHooks.test.tsx`、协议 `test_hooks.py`，技术说明见 [流程钩子](workflow-hooks.md)。

共享 Docker 镜像由根目录 `Dockerfile` 构建，包含 daemon、Gateway、两个前端、Gateway 工作台与官网；`docker-compose.yaml` 的 `workstep` / `gateway` 两个独立 service 分别启动 `main:app` / `gateway.app:app`，共用镜像内 daemon 虚拟环境，使用不同宿主端口和独立 Home 挂载。网关补充依赖由 `scripts/lock-container-gateway.py` 以 daemon 锁文件为约束生成到 `container-gateway-requirements.txt`；构建边界检查见 `scripts/tests/test_shared_image.py`，真实镜像启动与临时 Home 持久化验证见 `scripts/verify-shared-image.py`。部署见 [容器运行时](container-runtime.md)。

Web 与 Gateway 门户共用的设备 Tabs、通知中心、Android 通知桥接、票据跳转和组件 CSS 归 `packages/gateway-ui/src/` 所有，通过本地包依赖 `@workstep/gateway-ui` 使用；两应用不得直接导入对方 `src`。Web `GatewayDeviceTabs` 持有设备和授权项目请求，`GatewayWorkspaceNotifications` 组装公共通知中心；门户的同名旧入口重导出公共实现以兼容调用方。行为回归见 Web `completionNotifications.test.ts`、`gatewayWorkspaceFrame.test.tsx` 和门户 `notifications.test.tsx`、`my-workstep.test.tsx`、`android-notifications.test.tsx`。

安卓网关工作台资源 404：Web `vite.config.ts::experimental.renderBuiltUrl` 保持 HTML 入口绝对路径（由 Gateway `workspace_paths.py::rewrite_workspace_html` 加设备前缀），JS／CSS 内资源按源模块解析，防止延迟预取落到平台根 `/assets/`；回归 `apps/web/tests/workspaceAssets.test.ts` 执行实际构建的预取逻辑并检查跨设备、普通分享深链接。安卓通知根任务／会话链接归门户 `LegacyCompletionDestinationPage.tsx` → Gateway `notifications_api.py::legacy_access`：完成记录尚未采集或已清理时，按 `gateway/设备/项目` 范围重新核验设备／已发布项目授权并签发票据，不把缺少通知记录误判为访问失效；回归 `test_android_notification_access.py` 覆盖任务／会话、设备／项目授权、来源隔离、离线、撤销及慢目录读取健康 canary。

Codex CLI/SDK 思考强度由 `services/engine_config_rules.py::CODEX_REASONING_EFFORTS` 定义官方原生值（`none/minimal/low/medium/high/xhigh/max/ultra`）；`auto` 仅表示不发送覆盖值。`engines/codex.py` 与 `codex_sdk.py` 为 `core/base.py::resolve_thinking_effort` 指定 Codex 档位集合，按原值传到 CLI 配置及 SDK 新建／恢复会话，不借用其他引擎的降档映射。前端 `components/CoordinatorConfigBar.tsx::getThinkingEffortLevels` 按实际引擎选择档位，复用于对话配置与 `pages/AgentAssistantSettings.tsx`；`ChatInput.tsx` 显示已选档位。配置 API、默认值持久化仍由 `api/assistant.py`、`api/engine.py` 和 `services/config.py` 持有；具体模型是否支持所选档位由 Codex 判断。回归入口为 `tests/test_p2_engines.py::test_codex_sdk_spawn_injects_custom_config_and_skips_managed_keys`、`tests/test_assistant_api.py::test_assistant_config_accepts_native_efforts` 与 Web `tests/coordinatorThinkingEffort.test.tsx`。

DeepSeek Harness 连续会话由 `engines/deepseek_harness.py::_acquire_pooled/spawn` 持有：按项目和运行时配置指纹保留 SDK 子进程，首次握手加锁并在线程中完成，不按空闲时间回收，不自动换 ID 回退空会话。会话 ID 经 `agent_assistants/engine_invocation.py::run_engine_turn`、`base.py` 和 `chat_row_persistence.py` 保存／恢复，聊天入口是 `api/chat_session.py`。回归见 `tests/test_deepseek_harness_engine.py`（配置交错、并发启动、恢复冲突、慢指纹 canary）、`tests/test_deepseek_harness_chat.py`（真实 API 连续会话、SQLite ID 恢复、慢 SDK 初始化健康检查）；`scripts/verify_deepseek_session.py` 用已配置真实供应商在临时项目中验证三轮上下文、ID／PID 复用和独立会话隔离。SDK 运行时关闭后的原生日志恢复仍受上游限制，详见引擎开发指南。

本地项目的重启快捷按钮 `.workstep/actions/restart-workstep/workstep_restart_action.py` 转发到版本化 `scripts/workstep_restart.py`：独立执行器加文件锁串行重启，通过监听端口、工作目录和启动命令识别本项目服务，兼容失效 PID 文件与重复启动器；只向已验证的服务发送终止信号，排除引擎、执行器及其子进程，并校验进程启动时间以防 PID 复用。停止前检查工具、后台导入和官网构建，启动后核对新启动器的监听子进程及健康响应；`--check` 仅输出目标。`start.sh` 拒绝重复占用端口，避免覆盖 PID 文件或把旧健康响应误报成新后台就绪。模拟进程、独立执行器存活与启动失败回归归 `scripts/tests/test_workstep_restart.py`。

缺失 API 的网页回退边界由 daemon `main.py::_spa_fallback` 持有：`/api` 与 `/api/` 下未匹配路由一律返回 JSON 404，不能回退成首页或静态文件。Web `api/transport.ts::readApiResponse` 为普通及分享请求统一识别 HTML 响应，提示检查后台更新和重启；流程事件详情仍由 `hooks/useWorkflowMessageEvents.ts` 管理独立读取错误与重试，不改变回复执行状态。行为入口为 daemon `tests/test_spa_api_fallback.py`、`tests/test_workflow_gen.py::test_workflow_event_details_api_replays_journal_off_loop` 和 Web `tests/apiResponse.test.ts`、`tests/useWorkflowMessageEvents.test.tsx`。

Compose Home 复用由 `apps/desktop/src/sandbox.cjs::claimRoot` 校验目录布局并记录 `preserveHome`，`remove` 仅清理自有管理目录，保留复用 Home；准备失败重试和删除的数据保留、未知目录及符号链接拒绝均在 `apps/desktop/tests/sandbox.test.cjs` 覆盖。

子代理统一事件字段由 `apps/daemon/engines/core/plans.py::subagent_event` 定义：`task_id/status/stage` 和可选 `agent_name/agent_path/prompt/started_at/ended_at/result`，并兼容已有 description、summary 和嵌套事件。`core/subagents.py::SubagentTracker` 在 `AcpEngineBase.normalize_event` 保留真实委派工具输入及生命周期时间，冻结完成／中断时间，晚到结果不增加耗时；没有启动或输入来源时不补造。Claude/Qoder 的原生任务帧、Codex CLI/SDK 的协作快照、OpenCode 的委派工具和 Pydantic AI 的 run 回调各自提取原生字段。Codex SDK `codex_sdk_events.py` 将 `subAgentActivity` 按 `agentThreadId` 归一、按活动 ID 去重，启动和完成后使用 SDK `AsyncThread.read(include_turns=True)` 异步读取真实子线程输入与正文；`codex_sdk.py` 的普通／计划回合及目标回合调度读取，取消时清理任务，读取失败保留已有生命周期。事件经 `core/agui.py` 转为 `CUSTOM workstep.subagent`；Web `utils/messageTimeline.ts` 统一聚合实时与历史事件，`components/SubagentTimelineItem.tsx` 使用短名称、父级时钟、固定终态耗时、层级详情和可折叠复制的任务指令，没有输入时显示未提供。行为入口为 daemon `tests/test_subagent_contract.py`、`test_codex_subagent_activity.py`、`test_subagent_routing.py`、`test_pydantic_subagent_progress.py` 和 Web `tests/messageTimeline.test.ts`、`subagentProgress.test.tsx`。

桌面沙箱生命周期由 `apps/desktop/src/sandbox.cjs` 持有，提供辅助软件、镜像缓存、项目挂载的分步准备，并公开健康状态、实际端口、脱敏诊断日志和日志目录；`sandbox-startup-window.cjs` 与对应本地页面在后台可访问前展示 Podman、镜像、容器和健康检查进度，启动失败弹窗保留阶段与诊断路径。`sandbox-runtime.cjs` 负责校验下载与解包，`sandbox-docker.cjs` 负责本地 Docker 镜像扫描、架构过滤、导出及 Podman 导入与身份校验，`sandbox-config.cjs` 持有 WorkStep 配置迁移白名单、供应商冲突/绑定重映射和所选项目容器路径映射，`sandbox-ipc.cjs` 负责可信窗口、原生目录授权、日志读取/复制和活动工作检查；`main.cjs` 选择容器或 sidecar 后台并统一退出停止。前端 `components/SandboxSettings.tsx` 自管理五步引导（辅助软件、镜像、项目目录、迁移配置、确认）、管理页、镜像切换、内嵌日志、运行诊断、进度、备份导入与数据保留/切换确认，`SandboxImagePicker.tsx` 管理镜像扫描及选择；`SettingsPage`/`SettingsNavigation` 仅组装并保护未保存设置，沙箱入口位于导航末项且仅桌面显示。行为测试为桌面 `sandbox.test.cjs` / `sandbox-startup-window.test.cjs` / `sandbox-wizard.test.cjs` / `sandbox-config.test.cjs` / `sandbox-docker.test.cjs` 与 Web `sandboxSettings.test.tsx` / `sandboxImagePicker.test.tsx`；桌面发布工作流注入镜像摘要，说明见 `docs/desktop-sandbox.md`。

引擎图片输入由各适配器持有：`engines/core/acp_base.py`、`agent_assistants/engine_invocation.py` 和任务协调助手 `agent_assistants/coordinator.py::_invoke` 原样传递正文与 `EngineImage`，不按 `supports_vision` 注入提示词或清空附件。Claude Code/Agent SDK 使用 `engines/claude_image_input.py::build_claude_user_content` 直接发送原生图片内容块，保留原始正文；CLI 有图片时自动使用 stream-json 输入，即使没有实时消息队列。Codex CLI 使用重复的 `--image` 参数原生传入本地图片；恢复和失败重试继续携带当前回合附件，已建立会话后的纯文字插入不重复附图；非本地图片明确报错。Codex SDK 通过 `engines/codex_image_input.py` 使用官方 `TextInput` / `LocalImageInput` / `ImageInput`，计划和目标模式的原生 turn-start 同样携带图片，持久化目标仍为纯正文；两者均声明 `supports_vision` 且不追加路径提示，提示词快照只记录正文和图片引用，内联 data URL 仅显示「内联图片」标记。OpenClaw、Cursor SDK 和 Qoder SDK 在自身发送入口选择 `engines/core/image_input.py::render_image_prompt` 路径提示；Pydantic AI 在引擎内检查实际供应商模型的图片能力，支持时传原生图片，否则使用路径提示；原生 ACP 根据握手能力发送图片块，不支持时明确报错。DeepSeek Harness 保持明确拒绝图片输入。行为测试见 `tests/test_engine_vision.py`（含慢模型配置读取、慢图片读取的事件循环 canary，以及 Claude CLI 新建/恢复、普通/实时输入）、`tests/test_coordinator.py`（真实任务聊天 API 透传图片）、`tests/test_engine_system_prompt.py`（Codex SDK 普通/助手入口、新建/恢复与正文和图片分离）、`tests/test_codex_image_input.py`（CLI 新建/恢复、失败重试、实时插入和 SDK 计划图片输入）、`tests/test_p2_engines.py`（目标模式原生图片与纯文字目标）。

桌面非沙箱安装环境由 `apps/desktop/backend/server.py::prepare_runtime_environment` 持有，在加载 daemon 前将 npm 全局安装、uv 安装及解释器下载统一到配置目录的 `runtime/`，并注入 CLI PATH 和 Python 子进程 PYTHONPATH；Windows npm 命令位于 prefix，macOS/Linux 位于 prefix/bin。Volta 管理的宿主 npm 会先解析实际工具路径，以保证引擎安装仍写入 WorkStep 目录。后台自带 Python 随安装包分发，宿主机原有引擎继续作为回退。测试为 `apps/desktop/tests/test_backend_entry.py`，覆盖配置目录、子进程导入、离线 npm 安装/更新、重复初始化与加载 daemon 前初始化。

容器 Home 持久化由根目录 `Dockerfile` 与 `scripts/container-entrypoint.sh` 持有：基础运行时位于 `/root/.workstep/runtime/base`，镜像保留 Home 外的安装包；空 Home 首次离线初始化，安装包摘要变化时只替换基础运行时，并保留 npm/Python 引擎、Volta 下载和引擎配置。`scripts/prepare-container-runtime.py` 在构建时转换 terminfo 目录以兼容大小写不敏感的宿主文件系统；入口使用真实文件锁串行初始化，再执行镜像锁定的 daemon 虚拟环境。行为测试为 `scripts/tests/test_container_entrypoint.py`，挂载及迁移说明见 `docs/container-runtime.md`；根目录 `docker-compose.yaml` 使用 `./data/home:/root` 与独立项目挂载，保留本地构建入口；桌面沙箱设置和管理入口见上方条目。

官网渠道能力介绍由 `apps/landing/src/components/Channels.tsx` 持有，`App.tsx` 在流程模板与远程协作之间装配；中英文文案在 `src/i18n/zh-CN.ts` 与 `en-US.ts`，说明项目渠道对话、任务群绑定、阶段结果与附件推送、群内审核及确认。`Philosophy.tsx` 与 `Compare.tsx` 按工具路线呈现侧重点，不点名竞品。官网只展示能力，不调用渠道 API；实际渠道职责见下方渠道机器人条目。页面装配与文案回归在 `apps/landing/tests/positioning.test.tsx`，词典一致性见 `i18n.test.ts`。

后端异步 I/O 与分层优化：daemon `agent_assistants/coordinator.py` 的流式日志使用 `TurnEventJournal.arecord`；`event_journal.py` 在事件循环管理刷新定时器，专用线程执行写盘，存储锁保护日志线程与项目数据库线程的并发访问，防止刷新清空新追加事件。`engines/deepseek_harness.py` 在线程中解析项目路径，`ProjectContext` 拒绝异步数据库激活，数据库工作统一走 `ProjectManager.run_db`。`main.py` 将远程项目客户端注入 `WorkflowRuntime` → `TaskDispatchService`，服务不反向读取 API 全局变量。归档草稿校验、加载、保存与记忆写入回滚归 `services/task_archive.py`，`api/task_archive.py` 仅编排接口并提交数据库工作单元。行为入口为 `tests/test_coordinator.py`、`test_event_journal.py`、`test_deepseek_harness_engine.py`、`test_backend_layering.py`、`test_gateway_archive_message_scope.py` 和 `test_task_channel_unbinding.py`，覆盖慢盘/慢路径健康检查、事件不丢失、远程客户端注入和归档跨任务隔离。

远程项目添加校验与连接身份使用 `main.py::_local_actor`：优先采用当前已认证网关请求身份，其次采用设备已登录的网关账号（显示名称为空时使用平台用户名），无需填写本地使用者名称；连接仍携带当前设备身份。未连接网关时保留原有本地名称要求。回归入口为 `tests/test_remote_project_gateway_identity.py`。
远程项目每次 HTTP 请求的作者归属由 `api/remote_project_proxy.py` 从已认证 actor 上下文写入 `RemoteHttpRequest.actor`，`services/remote_project.py` 随普通或分块请求传输，`streaming/remote_host.py::RemoteRouteDispatcher` 在执行路由时替换作者 ID、名称和用户名，避免长连接把不同网关用户记为设备用户。设备身份、项目范围、访问级别仍取自连接凭据，不能由归属字段扩大权限；旧客户端缺少该字段时兼容原连接作者。链路测试覆盖同一连接多个网关用户、消息作者字段及分块请求；身份测试覆盖权限保持和旧协议回退。A、B 两端均须更新才能保留每次请求作者。
`api/remote_project_proxy.py::RemoteProjectProxyMiddleware` 在 `main.py` 中位于 `DesktopSecurityMiddleware` 内层，先鉴权与核对项目范围，再转发已登记的远程项目。整设备授权用户可走「网关 → 设备 A → 内网宿主 B」两段转发，A 使用原有 B 的项目凭据；只获 A 单项目授权的会话不能借此访问其它远程项目。`streaming/ws.py` 的远程订阅通过线程读取注册信息，B 的事件经 `RemoteProjectClientManager` 重写为 A 的远程项目 ID，再回传网关工作台。行为入口为 `tests/test_gateway_remote_project_chain.py`（真实桥接、远端鉴权/RPC、读写、事件回传、跨项目拒绝及慢远端健康 canary）、`test_desktop_security.py`、`test_remote_project.py`、Web `gatewayPlatformSettings.test.tsx` 和 `projectPublicationSettings.test.tsx`。
