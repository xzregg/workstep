# 渠道机器人：项目默认绑定与任务群绑定

> 状态：企业微信与钉钉的首版接入、配置和任务群绑定已实现；仍需使用真实平台租户验证收发与权限配置。

## 核心规则

一个企业微信或钉钉机器人足够服务多个项目与任务，不要求每个项目创建机器人。机器人负责连接平台；**消息来源的会话标识**决定实际去向。

1. 机器人可设置一个默认绑定，目标是项目或任务。单聊、没有专门绑定的群聊走默认绑定；没有默认绑定时不进入任何项目。
2. 在任务设置里选择机器人并填写平台群标识，将该群绑定到此任务。同一机器人可以接入多个群，各群可对应不同任务。
3. 收到群消息时，先查 `(平台, 机器人 ID, 群标识)` 的任务绑定。命中后调用该任务的**协调助手**，消息进入任务现有的协调对话与历史；助手回复发回原群。
4. 未命中任务群绑定时，才使用机器人默认绑定。默认目标为任务则同样进入任务协调助手；为项目则进入项目级渠道聊天会话。不能根据当前前端所选项目猜测目标。
5. 一个群同一时间最多绑定一个任务。改绑要明确显示旧目标；停用任务或删除绑定后不再把消息送往旧任务。

示例：机器人 R 的默认目标是项目 P。群 G1 绑定 P 的任务 T1，群 G2 绑定任务 T2；G1 的发言进入 T1 协调助手，G2 进入 T2，私聊机器人则进入 P 的项目会话。机器人无需复制三份。

## 接入与归一化

企业微信智能机器人使用官方 Python SDK 的 WebSocket 长连接；钉钉企业机器人使用官方 Python Stream SDK。daemon 主动连平台，不依赖公网回调，也不使用只会推送通知的群 Webhook 机器人。[企业微信 SDK](https://github.com/WecomTeam/wecom-aibot-python-sdk)、[钉钉 SDK](https://github.com/open-dingtalk/dingtalk-stream-sdk-python)。前端 `/ws` 仍只承载 WorkStep 页面状态。

入站消息统一为 `{bot_id, platform_message_id, conversation_type, conversation_id, sender_id, text}`。群标识取平台稳定的会话 ID，不用群名；设置页应提供从最近收到的群消息复制标识的方式，避免手填易错。首版处理单聊与群聊文本，其它消息类型明确提示暂不支持。

平台回调先确认并快速投递，模型处理和回复在独立异步任务中完成。用 `bot_id + platform_message_id` 作为任务协调助手的幂等键，同一群串行提交，避免重连重投或并发消息打乱上下文。平台回复失败只影响发送，不重复提交已持久化的协调消息。

## 持久化与权限

- 机器人及凭证是全局配置，沿用 `~/.workstep/config.json` 的锁、原子写和当前用户文件权限。每个机器人有 WorkStep UUID、平台、名称、平台应用标识、凭证、启用状态与默认绑定。API 只返回是否已有 Secret，不回显 Secret。
- 群与任务的绑定索引与机器人配置一同存放在全局配置中，键为 `(bot_id, 平台群 ID)`，记录项目 ID、任务 ID、创建和更新时间。这样路由时能直接找到项目，并在本机原子地保证同一个机器人群只绑定一个任务。任务设置经后端接口管理该索引；创建或改绑时用项目数据库执行器验证任务属于目标项目。任务被删除时清理索引；若外部状态变化留下悬空绑定，路由时拒绝投递并提示修复。
- 如果机器人默认绑定项目 P，群可以绑定 P 中的任务；需要跨项目使用同一个机器人时，允许群显式绑定其它项目的任务，但列表和任务设置必须显示项目名，避免误路由。默认绑定任务也只影响未单独绑定的会话。
- 协调助手调用现有 `CoordinatorModule.submit_message(project_id, task_id, content, idempotency_key, author_name=...)`。用户消息和助手回复共用任务现有历史；外部发言者通过 `author_name` 标明平台与昵称，具体身份映射在接入时核定。
- 禁用或删除机器人时关闭连接并停止新消息投递；历史任务对话保留，群绑定随机器人删除而移除。原个人微信 `channels` 与 `channel_chat_mappings` 表留在旧项目数据库中供历史兼容读取，不迁移为企业机器人凭证，也不重新启用旧连接。

## 界面

- 全局设置提供机器人列表、添加、编辑、连接状态、启停与删除。创建机器人时选企业微信或钉钉，并填平台提供的凭证和默认绑定。
- 任务设置提供「讨论群」区：选机器人、填写或选择最近收到的群标识、保存绑定、查看当前绑定及解绑。群绑定是任务级配置，不能只放在全局渠道页。
- 群内回复来自该任务协调助手；任务详情中能看到群成员发言与协调助手回复，标明外部来源。网页内的协调消息和群消息使用同一个任务对话，不另开一套群聊天状态。
- 连接异常、群标识冲突、任务已删除与助手运行失败都给出清晰状态；Secret 不进入浏览器列表、实时事件或日志。

## 实施顺序与验证

1. 建立机器人配置、群绑定模型和路由的失败测试：一个机器人两个群对应两个任务、默认项目/任务回退、跨项目显式绑定、重复消息、改绑与解绑。
2. 接入企业微信和钉钉长连接适配器，并与现有协调助手及项目级渠道助手对接；使用 SDK 模拟客户端测重连、回执、异步回复、停用与恢复。慢数据库/慢 SDK 配合健康检查，证明事件循环仍可响应。
3. 实现全局机器人设置与任务「讨论群」区，更新 `docs/code-map.md`、架构文档和四份词典。测试任务设置关闭保护、群标识冲突、连接状态与项目切换。
4. 用两平台测试租户分别验证单聊、群聊、任务历史回放和两个群的实际路由。凭证缺席的自动化测试只使用模拟客户端。

## 待确认的产品细节

- 当前方案把一个群的所有成员放进该任务现有的协调对话。这样群讨论和网页讨论能互相看到上下文，也意味着群成员发言可影响同一任务的协调决策。
- 群标识优先由最近收到的群消息选取；平台若不允许枚举群列表，界面应显示机器人接收到的最近群会话，而非声称能浏览企业所有群。
