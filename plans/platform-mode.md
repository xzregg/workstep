# WorkStep 平台模式实施计划

> 状态：提案，尚未实现。本文描述未来的平台登录、用户、权限、平台数据库和审计方案，不代表当前产品能力。

## 1. 目标

在保留现有本地优先工作方式的基础上，增加可动态开启、无需重启的“平台模式”。平台模式由独立网关提供用户注册登录、设备连接与分配、HTTP/WebSocket 代理、项目可见性管理和操作审计；每台 WorkStep PC 继续运行自己的 Web、daemon 和每项目独立 SQLite 数据库。

平台网关总体结构图：

- [平台网关模式架构图](./platform-gateway-architecture.html)

本计划的核心目标：

- 平台模式可以在系统设置中即时开启或关闭，不重启 daemon。
- 平台模式开启后，用户必须注册并登录才能进入平台。
- 其他电脑安装 WorkStep 后配置网关地址，由本机软件主动建立 WebSocket 长连接。
- 网关能展示在线/离线 PC、PC 分配用户和最近连接状态。
- 网关集中管理可用的 LLM 供应商、模型、价格和分配策略，并通过设备隧道把授权配置下发到各 PC。
- 用户在网关选择获分配的 PC 后，网关通过设备长连接代理该 PC 的 HTTP 与 WebSocket，从而加载并操作其 WorkStep 界面。
- 平台主数据库固定为 `<网关平台根目录>/workstep_platform.db`。
- 普通用户在某台 PC 上创建的项目只能位于该 PC 的 `<受管项目根目录>/projects/{username}/{项目目录}`。
- 管理员创建的共享项目可以指定任意本机绝对目录。
- 项目以“是否对当前用户可见”作为统一访问边界，不为每个业务接口设计独立角色权限。
- 普通用户创建的项目默认仅自己可见，可分享给其他平台注册用户。
- 管理员可以创建共享项目并分配可见用户。
- 本地模式和平台模式下，每一条新消息都必须记录用户名或明确的系统身份。
- 任务启动、排队、暂停、恢复、停止、取消、审核等关键动作必须持久化记录操作者。
- 网关按用户、PC、项目、供应商和模型汇总 Token 用量与估算成本，并能区分网关权威计量和 PC 回传计量。
- 现有项目级数据库继续位于 `<项目目录>/.workstep/workstep.db`。

## 2. 已确认的产品规则

### 2.1 运行模式

系统存在两种模式：

- `local`：现有本地模式，不要求登录，使用系统设置中的本地用户名和设备身份。
- `platform`：平台模式，必须登录，项目列表和项目访问按当前用户的可见项目过滤。

模式切换规则：

- 切换不重启 daemon。
- 模式配置更新后立即作用于新请求。
- 正在执行的任务不被中断，继续使用启动时持久化的发起人身份。
- 模式变化通过全局事件通知前端；前端更新路由状态并重新建立 WebSocket 身份。
- 关闭平台模式不删除平台数据库、用户、项目登记或审计记录。
- 再次启用同一网关平台根目录时恢复原平台数据。
- 更换网关平台根目录不自动迁移原平台数据库；各 PC 的项目文件不随之移动。

### 2.2 网关与 PC 目录

网关平台目录只保存控制面数据：

```text
<网关平台根目录>/
└── workstep_platform.db
```

每台 PC 独立配置本机受管项目根目录：

```text
<PC 受管项目根目录>/
└── projects/
    ├── zhangsan/
    │   ├── project-a/
    │   └── project-b/
    └── lisi/
        └── project-c/
```

普通用户创建项目：

- 用户先选择自己获分配的在线 PC，前端只提交项目名称，不提交物理路径。
- 目标 PC 的 daemon 根据网关签名用户生成本机项目路径。
- 路径固定在该 PC 的 `<受管项目根目录>/projects/{username}/` 下。
- 普通用户不能注册该 PC 受管项目根目录外的已有项目。
- `username` 是稳定目录标识，创建后不可修改。
- 展示名称 `display_name` 可以修改，不影响目录。

管理员在选定 PC 上创建共享项目：

- 可以指定任意本机绝对目录并初始化新项目。
- 可以注册任意已有 WorkStep 项目。
- 真实路径只由目标 PC 解析和使用；网关登记设备 ID、项目 ID 和展示元数据，不使用该路径访问文件。
- 取消平台注册默认只删除登记和可见关系，绝不删除本机目录。

管理员外部路径仍需通过基础安全校验：

- 必须是绝对路径。
- 使用 `resolve()` 得到规范路径。
- 禁止直接把 `/`、用户主目录、PC 受管项目根目录本身或网关平台根目录本身注册为项目。
- 不允许两个项目登记到同一个规范路径。
- 检查读写权限。
- 非空且不是有效 WorkStep 项目的目录不得直接初始化。
- 检测符号链接、重复路径及父子项目嵌套，并阻止高风险情况或要求明确确认。

### 2.3 项目可见性

项目只有两种可见性：

- `private`：仅项目所有者和管理员可见。
- `shared`：所有者、管理员以及被分配用户可见。

项目来源：

- `user_managed`：普通用户创建，路径受平台目录限制。
- `admin_external`：管理员指定任意本机目录创建或注册的共享项目。

管理规则：

- 普通用户创建项目后自动成为所有者，项目默认为 `private`。
- 项目所有者可以添加或移除自己项目的可见用户。
- 管理员可以管理全部项目的可见用户。
- 管理员共享项目可以不指定普通用户所有者，只由管理员维护共享名单。
- 被分享用户获得项目现有功能的使用能力；第一版不再细分只读、编辑者等角色。

“不需要每个接口都授权”的实现含义是：

- 不在每个业务接口重复实现角色和权限判断。
- 所有项目访问统一通过项目解析/数据库执行入口检查项目是否对当前用户可见。
- REST、WebSocket、文件、上传、搜索和统计均复用同一检查结果。
- 前端隐藏不是安全边界；后端必须阻止通过猜测 `project_id` 的越权访问。

### 2.4 身份与消息署名

无论本地模式还是平台模式，每条新消息都要保存不可为空的作者快照。

统一字段语义：

- `author_id`：作者稳定标识。
- `author_username`：消息创建时的用户名快照。
- `author_name`：消息创建时的显示名称快照。
- `author_type`：`user`、`assistant`、`system` 或 `scheduler`。
- `initiated_by_user_id`：触发系统、助手或定时行为的原始用户。
- `initiated_by_username`：原始发起用户名快照。
- `author_device_id`、`author_device_name`：设备快照，保留现有远程项目能力。

记录规则：

| 消息来源 | author | initiated_by |
|---|---|---|
| 本地用户发送 | 系统设置中的本地用户名 | 同一用户 |
| 平台用户发送 | 当前登录用户 | 同一用户 |
| 助手回复 | 助手或引擎身份 | 启动该轮的用户 |
| 系统可见消息 | `system` | 存在原发起人时记录 |
| 定时任务消息 | `scheduler` | 创建或最后启用计划的用户 |
| daemon 恢复执行 | `system` | 原任务运行的发起用户 |

本地模式要求：

- 首次使用仍要求设置本地用户名。
- 本地用户名为空时，不允许发送消息或启动任务。
- 本地用户稳定标识继续使用设备 ID。
- 历史缺失作者的消息显示“历史用户”，不得回填或伪造成当前用户。

覆盖的消息类型：

- 任务执行消息和阶段中途消息。
- 任务协调助手消息。
- AI 流程助手消息。
- 任务创建助手消息。
- 独立聊天会话消息。
- 人工审核消息。
- 系统生成且前端可见的消息。

## 3. 总体架构

### 3.0 平台网关定位

平台模式不再理解为“在单个 daemon 外增加登录页面”，而是由一个独立部署的网关把多个 WorkStep PC 汇聚为可登录、可分配、可代理访问的平台。

职责边界：

- 平台网关是控制面：管理注册用户、登录会话、设备、用户与设备分配、供应商配置、在线状态和全局审计。
- 平台网关也是访问入口：用户点击某台 PC 后，网关代理浏览器 HTTP 请求和 WebSocket 连接到目标 PC。
- WorkStep PC 是执行面：继续运行本机 Web、daemon、引擎、项目数据库和文件系统，网关不接管任务执行。
- PC 主动向网关建立 `wss://` 长连接，不要求 PC 暴露公网端口，也不依赖网关主动拨入内网 PC。
- 每条设备隧道需要支持多路复用，至少承载请求/响应式 HTTP 流与长生命周期 WebSocket 流。
- 同一设备隧道也承载版本化配置清单、配置应用回执和用量事件；这些控制帧与代理业务流使用不同的消息类型和流 ID。

核心访问路径：

```text
用户浏览器
  → 登录平台网关并取得平台会话
  → 查看本人获分配且当前可访问的 PC
  → 点击 PC，网关签发短期设备访问票据
  → 网关把 HTTP / WebSocket 流复用到该 PC 的 WSS 设备隧道
  → PC 连接代理验签并把请求交给本机 FastAPI / WebSocket 路由
  → 浏览器获得该 PC 的 WorkStep 前端和实时交互能力
```

这与现有远程项目能力的方向相近：传输保持 HTTP 语义，WebSocket 用作 daemon 间承载通道，FastAPI 仍是路由、校验和错误处理的权威入口。新平台网关需要把现有“项目级远程连接”提升为“设备级完整界面代理”，但不能让浏览器提供的普通请求头直接成为可信身份。

### 3.0.1 设备身份与用户分配

平台主数据库新增或扩展以下关系：

- `devices`：设备 ID、设备名称、公钥或凭据摘要、版本、能力、状态、首次/最后连接时间。
- `device_connections`：当前连接 ID、建立时间、心跳时间、断开原因和网关实例；历史记录按保留策略清理。
- `user_devices`：用户与设备的多对多分配关系、分配人、分配时间和状态。
- `proxy_sessions`：用户点击 PC 后形成的代理会话，记录用户、设备、开始/结束时间、结果和流量摘要，不记录敏感正文。

管理员可以查看所有注册 PC、在线状态和分配用户；普通用户只能看到分配给自己的 PC。设备分配是进入整台 PC 的第一层访问边界，项目可见性仍由目标 PC 的项目解析层执行，二者不能互相替代。

### 3.0.2 可信代理身份

网关转发身份必须使用短期签名票据或等价的双方认证机制，不能只注入可由浏览器伪造的 `X-WorkStep-*` 请求头。票据至少绑定：

- 平台用户 ID、用户名和显示名称快照。
- 目标设备 ID。
- 代理会话 ID。
- 签发、过期时间与一次性随机值。
- 必要时绑定请求或 WebSocket 流 ID。

PC 的连接代理验签并确认目标设备后，才把平台身份转换为 `CurrentActor`。此身份继续进入消息作者、任务启动/暂停等审计和后台发起人传播链路。

### 3.0.3 代理路由与前端约束

建议使用稳定的设备作用域路由，例如：

```text
/devices/{device_id}/...                 # HTTP 与前端静态资源
/devices/{device_id}/ws                  # 主事件 WebSocket
```

网关负责路径改写、WebSocket upgrade、Cookie/Location 作用域和流式响应，不解析业务响应正文。前端需要支持可配置 `base URL` 与 WebSocket URL，避免静态资源、API 和跳转逃离当前设备前缀。

设备离线、用户被取消分配、账户被禁用或平台模式关闭时，网关立即拒绝新代理流并关闭现有相关流；目标 PC 上已经启动的任务继续按持久化发起人身份运行。

### 3.0.4 供应商控制面与下发

网关集中维护供应商的非敏感配置、模型目录、价格版本和授权范围。PC 连接成功或配置版本变化时，通过设备隧道同步“期望配置清单”；PC 原子应用后回传已应用版本、状态和错误。断线重连只同步版本差异，删除或撤销通过 tombstone 明确传播，不能依赖盲目覆盖本机配置。

供应商配置必须拆成两部分：

- 元数据：供应商 ID、名称、协议、API 地址、模型白名单、价格版本、启用状态和分发模式，可以下发到获授权 PC。
- 凭据：API Key、访问令牌等秘密，不进入普通配置响应、日志、审计元数据或项目数据库。

支持三种来源或运行方式：

1. `gateway_proxy`（平台供应商的推荐默认）：Key 只保存在网关安全存储中，PC 获得平台代理地址和短期调用凭据，模型请求经过网关。该模式最适合集中撤销、限额和权威 Token 统计。
2. `device_secret`（兼容必须直连供应商的 CLI/SDK）：网关仅向指定 PC 发送使用该设备公钥加密的凭据包；PC 解密后写入系统凭据存储，普通配置只保存 secret reference。此模式无法防止目标 PC 的本机管理员提取凭据，应在界面明确风险。
3. `local`：PC 本地已有供应商，继续由设备所有者维护，不上传密钥，也不视为平台下发配置。

第一版优先实现 `gateway_proxy` 与 `local`。只有确认某类引擎无法使用代理协议时，才为该类引擎启用 `device_secret`，避免把平台密钥大范围复制到终端。

供应商授权必须同时检查用户和执行设备。仅“已下发到 PC”不代表该 PC 上的所有平台用户都可使用：启动任务时仍需满足当前用户可访问目标 PC、供应商已分配给该用户或设备、目标模型在允许列表内。平台供应商在 PC 端显示为只读配置，并使用稳定命名空间 ID（例如 `platform:<uuid>`），避免与现有本地供应商 ID 冲突。

PC 侧解析优先级固定为：项目显式绑定的平台供应商 → 用户平台默认供应商 → 设备平台默认供应商 → 本地供应商。最后一级只用于本地模式或平台明确允许的本地配置，不能静默绕过平台供应商策略。

### 3.0.5 Token 用量回传与集中统计

每次模型调用生成全局唯一 `usage_event_id` 和 `request_id`，用量记录至少包含：平台用户、原始发起人、执行 PC、项目、任务或会话、供应商、供应商配置版本、模型、输入/输出/缓存 Token、估算成本、计量来源和发生时间。

- `gateway_proxy`：网关在代理模型请求时生成权威用量记录；PC 只携带关联 ID，不再重复计费。
- `device_secret` 或 `local` 直连：执行调用的 PC 从标准化 `usage_update` / 最终响应中生成用量事件，经设备隧道回传；网关以 `usage_event_id` 幂等写入，并标记 `reported_by_device`。
- 远程项目：只由真正执行模型调用的项目宿主 PC 回传，访问该项目的入口 PC 不重复上报。
- 供应商账单核对：后续可按供应商的账单或用量 API 做周期性对账；第一版不能把缺失 usage 的调用错误统计为零。

价格按调用发生时的 `pricing_version` 或单价快照计算，历史成本不因管理员后来修改价格而变化。Token 统计用于产品用量与成本分析，不直接等同于供应商最终账单，除非该条记录来自网关代理或已完成供应商对账。

### 3.0.6 批量 PC 操作与命令编排

网关可以对选中的多台 PC 批量执行受支持的管理动作，例如安装、升级、回退或重新扫描某个引擎。其语义是“网关为每台目标 PC 创建一条有类型的设备命令”，目标 PC 收到命令后调用与本机按钮相同的应用服务。

本机页面、代理页面和网关设备命令必须复用同一个底层服务，例如都调用 `EngineRuntimeManager.start()`；不要让设备命令在 PC 内部再通过 loopback HTTP 请求自己的 FastAPI，也不要复制另一套安装逻辑。HTTP API 是本机点击的传输入口，设备隧道命令是另一个入口，二者共享校验、互斥、状态持久化和结果模型。

网关批量作业不是一个阻塞循环：

```text
管理员创建批量作业
  → 网关冻结目标 PC、动作、引擎和版本快照
  → 为每台 PC 创建独立 device_command
  → 按 max_concurrency 分批下发（设为 1 即严格轮流）
  → PC 接收并持久化命令，回传 accepted
  → PC 调用本机应用服务，持续回传 running / progress
  → 网关汇总 succeeded / failed / skipped / offline / expired
```

第一版只允许命令目录中的结构化动作，例如 `engine.install`、`engine.update`、`engine.rollback`、`engine.refresh`、`engine.test` 和 `provider.sync`。不得提供通用 shell、任意 URL 请求或让管理员提交命令行字符串。

命令必须包含管理员身份、目标设备、动作、参数、过期时间、唯一幂等键和签名；PC 验证设备目标、签名、动作白名单、参数 schema、版本兼容性及第三方条款确认后才能接受。

每台 PC 的安装互斥仍由本机运行时管理器负责。网关可以同时操作多台 PC，但同一 PC 已有安装任务时应返回 `busy` 或保留为等待状态，不能启动第二个安装进程。离线设备可以显示为 `offline`，是否排队等待重连由批量作业选项决定；等待命令必须有明确 TTL，过期后不得在数天后突然执行。

### 3.1 数据库分层

平台主数据库：

```text
<网关平台根目录>/workstep_platform.db
```

负责：

- 平台配置。
- 用户与登录会话。
- 设备注册、在线状态和设备连接历史。
- 用户与 PC 的分配关系。
- 浏览器到 PC 的代理会话审计。
- 项目注册信息、所属设备和展示元数据；真实路径的解析权留在目标 PC。
- 项目所有权与可见用户关系。
- 供应商元数据、用户/设备授权、配置版本和设备应用状态。
- Token 用量账本与聚合统计。
- 批量 PC 作业、逐设备命令和执行结果。
- 全局操作审计。

项目数据库：

```text
<项目目录>/.workstep/workstep.db
```

继续负责：

- 任务、阶段、消息、助手会话。
- 工作流、审核、产物和项目设置。
- 项目运行时数据。

平台主数据库使用独立的 Peewee 模型与独立执行器，不复用项目数据库的 `db_proxy` 激活上下文。所有异步路由、WebSocket 和后台协程中的平台数据库操作也必须提交到专用数据库线程执行。

### 3.2 运行时服务

建议新增以下职责边界：

- `PlatformModeService`：读取、校验并原子切换本地/平台运行模式。
- `PlatformDatabaseManager`：按当前网关平台根目录打开、关闭和切换平台主数据库。
- `AuthenticationService`：注册、登录、注销、会话校验和密码重置。
- `DeviceRegistryService`：设备注册、设备凭据轮换、在线状态和能力信息。
- `DeviceAssignmentService`：维护用户与 PC 的可访问分配关系。
- `DeviceTunnelManager`：接收 PC 主动建立的 WSS 长连接、心跳和多路复用流。
- `GatewayProxyService`：校验用户与设备分配，创建短期访问票据并代理 HTTP/WebSocket。
- `ProviderControlService`：维护平台供应商、授权范围、模型与价格版本，生成设备期望配置清单。
- `ProviderSecretService`：隔离供应商凭据；为网关代理取用密钥，或按设备公钥生成加密凭据包。
- `ProviderSyncService`：通过设备隧道同步配置版本、接收应用回执并处理撤销。
- `UsageLedgerService`：幂等接收模型用量、保存单价快照并生成用户/设备/项目维度统计。
- `DeviceOperationService`：创建批量作业、限制跨设备并发、处理离线策略并汇总结果。
- `DeviceCommandExecutor`：在 PC 上验证和持久化结构化命令，并调用与本机 API 相同的应用服务。
- `CurrentActorService`：统一生成本地或平台操作者快照。
- `PlatformProjectRegistry`：维护项目所属设备、稳定项目 ID、所有者和可见关系。
- `ProjectAccessResolver`：根据当前身份解析可访问项目，并作为统一访问门禁。
- `AuditService`：追加写入关键操作记录。
- `MessageIdentityService`：为所有消息生成完整作者和发起人字段。

不能让各助手、任务路由、文件路由分别拼装身份字段；必须统一从身份服务取得快照。

### 3.3 热切换状态

后端运行状态：

- `local`
- `platform_initializing`
- `platform_ready`
- `platform_unavailable`
- `switching`

切换过程：

1. 校验目标网关平台根目录。
2. 打开或创建 `workstep_platform.db` 并运行迁移。
3. 构建新的只读运行时配置快照。
4. 原子替换当前配置和数据库引用。
5. 发布模式变化事件。
6. 新请求使用新模式；旧请求和已运行任务使用开始时捕获的快照完成。

如果切换失败，保留原模式和原数据库引用，前端显示失败原因，不进入半开启状态。

## 4. 平台主数据库模型

### 4.1 `platform_settings`

- `key`，唯一。
- `value_json`。
- `updated_by_user_id`，可空。
- `updated_at`。

平台模式开关和网关平台根目录的最低引导配置保存在网关服务配置中，使网关能定位平台数据库；平台内部设置保存在主数据库。PC 只保存网关地址、设备凭据和本机受管项目根目录，不直接打开平台数据库。

### 4.2 `users`

- `id`。
- `username`，唯一、不可修改。
- `display_name`。
- `password_hash`。
- `role`：`admin`、`user`。
- `status`：`pending`、`active`、`disabled`。
- `created_at`、`updated_at`、`last_login_at`。
- `created_by_user_id`，首位管理员可空。

用户名建议仅允许 ASCII 字母、数字、下划线和短横线，统一小写或执行不区分大小写的唯一约束，避免跨平台路径冲突。

### 4.3 `auth_sessions`

- `id`。
- `user_id`。
- `token_hash`，不保存明文令牌。
- `created_at`、`expires_at`、`revoked_at`。
- `last_seen_at`。
- `device_id`、`device_name`。

### 4.4 `platform_projects`

- `id`，与项目自身稳定 ID 一致。
- `name`。
- `device_id`，项目所在的 WorkStep PC。
- `remote_project_id`，目标 PC 内的稳定项目 ID；与 `device_id` 组成唯一约束。
- `path_display`，可选的管理员展示快照，不作为网关访问文件的依据。
- `source_type`：`user_managed`、`admin_external`。
- `visibility`：`private`、`shared`。
- `owner_user_id`，管理员共享项目可空。
- `created_by_user_id`。
- `created_at`、`updated_at`。
- `status`：`active`、`unavailable`、`unregistered`。

### 4.5 `project_users`

- `project_id`。
- `user_id`。
- `assigned_by_user_id`。
- `created_at`。
- `(project_id, user_id)` 唯一。

该表只表达“额外可见用户”，项目所有者和管理员不需要重复写入。

### 4.6 `audit_events`

- `id`，建议 UUIDv7。
- `mode`：`local`、`platform`。
- `actor_type`。
- `user_id`、`username`、`display_name`。
- `initiated_by_user_id`、`initiated_by_username`。
- `device_id`、`device_name`。
- `action`。
- `project_id`、`task_id`、`step_key`、`run_id`、`message_id`。
- `result`：`success`、`failure`、`denied`。
- `metadata_json`，只保存经过白名单过滤的精简元数据。
- `request_id`。
- `created_at`。

审计记录只追加，不提供普通编辑和删除接口。不得记录密码、会话令牌、模型密钥或完整敏感消息正文。

### 4.7 `platform_providers`

- `id`，稳定平台供应商 ID。
- `name`、`type`、`protocols_json`、`base_urls_json`。
- `distribution_mode`：`gateway_proxy`、`device_secret`。
- `model_policy_json`、`pricing_version`。
- `enabled`、`revision`。
- `created_by_user_id`、`created_at`、`updated_at`。

该表不保存可直接返回客户端的明文 API Key。凭据使用系统凭据库、外部 Secret Manager 或独立加密记录，并以 `secret_ref` 关联。

### 4.8 `provider_assignments`

- `provider_id`。
- `scope_type`：`user`、`device`。
- `scope_id`。
- `enabled`、`is_default`、`priority`。
- `assigned_by_user_id`、`created_at`、`updated_at`。
- `(provider_id, scope_type, scope_id)` 唯一。

第一版不用组织和用户组。一次调用必须同时通过用户和执行设备的有效策略计算，不能仅凭 PC 已收到配置就授权使用。

### 4.9 `device_provider_state`

- `device_id`、`provider_id`。
- `desired_revision`、`applied_revision`。
- `status`：`pending`、`applied`、`failed`、`revoked`。
- `last_error_code`、`last_error_summary`。
- `last_sync_at`、`acknowledged_at`。
- `(device_id, provider_id)` 唯一。

错误摘要必须脱敏。管理员通过该表判断某台 PC 是否真正应用配置，而不是只看网关是否发送成功。

### 4.10 `usage_events`

- `id` / `usage_event_id`，全局唯一，用于幂等去重。
- `request_id`、`source`：`gateway_authoritative`、`reported_by_device`、`provider_reconciled`。
- `user_id`、`initiated_by_user_id`、`device_id`、`project_id`。
- `task_id`、`run_id`、`message_id`、`session_id`。
- `provider_id`、`provider_revision`、`model`。
- `input_tokens`、`output_tokens`、`cache_read_tokens`、`cache_write_tokens`、`total_tokens`。
- `currency`、`unit_price_snapshot_json`、`estimated_cost`。
- `occurred_at`、`received_at`。

明细账本追加写入，按日/用户/设备/项目/供应商生成可重建的聚合表或缓存。修改价格只影响后续事件，不重写历史明细。

### 4.11 `device_operation_batches`

- `id`、`action`、`parameters_json`。
- `created_by_user_id`、`created_at`。
- `max_concurrency`、`offline_policy`、`expires_at`。
- `target_count`、`status`。

创建后目标设备和参数保存为快照，后续设备筛选结果变化不能悄悄改变已创建作业。

### 4.12 `device_commands`

- `id`、`batch_id`、`device_id`。
- `action`、`parameters_json`、`idempotency_key`，其中幂等键唯一。
- `status`：`queued`、`dispatched`、`accepted`、`running`、`succeeded`、`failed`、`skipped`、`cancelled`、`expired`。
- `progress_json`、`result_summary`、`error_code`。
- `attempt_count`、`dispatched_at`、`accepted_at`、`finished_at`、`expires_at`。

PC 必须持久化最近处理过的命令 ID 与最终结果。网关因断线重发同一命令时，PC 返回原状态或结果，不重复安装。

### 6.3 用户管理

列表字段：

- 用户名、显示名称、角色、状态。

筛选：

- 用户名或显示名称。

操作：

- 启用或禁用。
- 重置密码。

用户名不可修改。已产生消息或审计记录的用户不物理删除，只允许禁用。

### 6.4 PC 与连接管理

列表字段：

- PC 名称、设备 ID、系统与 WorkStep 版本。

- 已分配用户数量、活跃代理会话数量。
- 本机受管项目根目录状态和项目数量摘要。

操作：

- 审批或拒绝新设备注册。
- 多选 PC 后批量安装、升级、回退、重新扫描或测试引擎。
- 修改 PC 展示名称。
- 分配或移除可访问用户。
- 撤销并轮换设备凭据。

- 停用设备；默认不删除目标 PC 上的任何项目文件。

设备详情页应明确区分“设备在线”与“daemon 健康”。WebSocket 连接存在但本机 WorkStep 无法处理请求时，状态应显示为故障而不是在线可用。

批量操作页按 PC 展示排队、已接收、执行中、成功、失败、离线和过期状态，并允许只重试失败项。创建作业前必须展示目标 PC 数量、引擎、确切版本、预计下载量、并发数和第三方条款；确认后不得因筛选条件变化而增减目标。

普通用户和 PC 端界面只能看到获授权的供应商名称、模型与可用状态，不能读取密钥。PC 端平台供应商为只读；本地供应商保持在单独分区，避免与平台配置混淆。

## 8. 统一项目访问流程

平台模式下：

```text
请求或 WebSocket 订阅
  → 解析登录会话
  → 得到当前用户
  → 根据 device_id 检查用户是否获分配该 PC
  → 根据 project_id 查询平台项目登记
  → 判断项目是否对用户可见
  → 通过设备隧道把 device_id、project_id 和签名用户身份交给目标 PC
  → 目标 PC 从本机项目注册表解析真实路径
  → 提交到该项目数据库执行器
```

客户端和网关都不得通过提交任意本机路径选择项目。普通业务访问只携带设备 ID 与项目 ID；项目真实路径只能由目标 PC 的本机项目注册表解析。管理员创建或注册外部项目时，路径输入也只发送给所选择的目标 PC 校验。

需要接入统一可见性解析的入口：

- 项目列表和项目详情。
- 任务、工作流、助手、计划任务、频道。
- 历史消息、事件日志、统计和搜索。
- 文件浏览、上传、产物和 Markdown 图片。
- WebSocket 任务、会话和频道订阅。
- 项目导出或公开分享创建。

远程项目和公开任务分享保留现有独立凭据模型，不自动转化为平台注册用户权限。

## 9. 消息和审计改造

### 9.1 消息入口收拢

当前任务消息和聊天消息已经有部分作者字段，但覆盖不完整。实施时建立统一消息身份填充函数，并使所有持久化入口调用它。

要求：

- 用户消息缺少有效用户身份时拒绝创建。
- 助手、系统和定时器消息也必须写入明确 `author_type` 和作者名。
- 助手回复持久化本轮 `initiated_by`，不依赖读取当前请求上下文。
- API 历史响应和 AG-UI 自定义字段统一返回作者快照。
- 前端 `MessageMetaBar` 统一渲染本地或平台作者。

### 9.2 后台身份传播

不能只依赖 `ContextVar` 传播身份。任务启动时把身份快照写入运行记录；队列等待、daemon 恢复、定时器触发和子任务接力都从持久化快照恢复。

需要覆盖：

- `WorkflowRun`。
- 助手会话轮次。
- 定时计划。
- 人工审核和交互响应。
- 跨阶段任务分发。

### 9.3 审计动作

第一版至少记录：

- 平台开启、关闭、根目录切换。
- 注册、登录成功、登录失败、退出、用户审核、禁用和密码重置。
- 创建、注册、取消注册项目。
- 项目可见性和成员变化。
- 创建、修改、归档、删除任务。
- 启动、排队、暂停、恢复、停止和取消任务或阶段。
- 人工审核、审批和交互答复。
- 定时计划创建、启用、暂停及触发。
- 消息创建失败等需要追责的异常。

普通消息正文仍以项目数据库为权威；审计表只保存消息标识和动作，不重复保存正文。

## 10. 前端全局状态

前端平台状态：

- `local`
- `platform_initializing`
- `platform_unauthenticated`
- `platform_authenticated`
- `platform_unavailable`

状态变化：

- 本地切换到新平台：进入 `/platform/setup`。
- 本地切换到已有平台：进入 `/login`。
- 平台关闭：退出管理路由并回到本地工作台。
- 用户被禁用：撤销会话并进入登录页。
- 当前项目可见性被撤销：关闭项目内容并跳转“我的项目”。
- 平台数据库暂不可用：展示明确故障页，不自动退回本地模式。

登录、用户管理、项目管理、审计和平台设置分别建立自管理组合模块；页面层只负责编排和路由，遵循现有前端拆分规范。

## 11. 实施阶段与验证

全程采用测试先行方式。每一阶段先增加失败测试，再实现最小功能使测试通过。

### 阶段 1：平台数据库与运行模式

工作：

- 建立平台数据库模型、迁移和专用执行器。
- 增加本地/平台配置快照及动态切换服务。
- 固定数据库文件名 `workstep_platform.db`。

验证：

- 开启、关闭无需重启。
- 失败切换能原子回滚。
- 切换过程中健康检查保持响应。
- 平台数据库慢 SQL 或 SQLite 锁竞争不阻塞事件循环。

### 阶段 2：注册、登录和身份

工作：

- 首位管理员初始化。
- 注册、审核、登录、注销、禁用和会话恢复。
- 统一本地及平台操作者快照。

验证：

- 未登录无法进入平台业务页面。
- 禁用、过期和撤销会话立即失效。
- 用户名大小写、重复和路径字符校验正确。
- 本地模式继续使用本地用户名和设备 ID。

### 阶段 3：设备注册、分配与代理隧道

工作：

- 建立设备注册、设备凭据和用户-PC 分配模型。
- PC 使用 WSS 主动连接网关，完成心跳、重连和连接替换。
- 建立 HTTP 请求/响应与 WebSocket 流的隧道多路复用协议。
- 网关创建短期签名访问票据，PC 验签后生成平台操作者快照。
- 建立结构化设备命令、批量作业、幂等回执、进度回传和过期处理。

验证：

- 网关准确展示 PC 在线、离线、版本和最后连接时间。
- 未获分配用户不能打开、枚举或建立到目标 PC 的代理流。
- PC 位于 NAT 后且没有入站端口时仍可被已授权用户访问。
- HTTP 流式响应、上传、下载和 WebSocket 双向消息均可正确转发与取消。
- 账户禁用、设备取消分配或设备断线时，相关代理流及时关闭。
- 恶意浏览器不能伪造网关身份或跨设备重放访问票据。
- 批量安装能按并发上限调度；设为 1 时严格逐台执行，单台失败不阻塞其他目标。
- 命令重发不会重复安装，离线命令过期后不会突然执行，任意 shell 或未知动作会被 PC 拒绝。

### 阶段 4：供应商控制面、下发与用量账本

工作：

- 建立平台供应商、授权关系、配置版本、设备应用状态和用量账本模型。
- 通过设备隧道实现期望配置清单、差量同步、回执、撤销和失败重试。
- 优先实现网关模型代理；保留本地供应商，按真实兼容需求再实现设备加密凭据下发。
- 把现有标准化 usage 事件映射为网关幂等用量记录。

验证：

- 未获分配的用户或 PC 不能发现或使用平台供应商。
- 配置重发、PC 重连和重复 usage 事件不会产生重复配置或重复计费。
- API Key 不出现在普通 API、WebSocket 日志、审计、项目数据库或前端状态中。
- 撤销或轮换后，网关代理立即拒绝旧凭据；在线 PC 收到新版本或撤销回执。
- 远程项目只由实际执行 PC 或网关代理记一次用量，入口 PC 不重复统计。
- Token 和成本可按用户、PC、项目、供应商、模型汇总，并保留价格快照和计量来源。
- 网关数据库慢写、供应商网络延迟或 PC 回传阻塞时，FastAPI 事件循环健康检查仍及时响应。

### 阶段 5：平台项目登记与目录策略

工作：

- 建立项目登记、所有者和可见用户关系。
- 普通用户受管项目创建。
- 管理员任意目录共享项目创建与注册。

验证：

- 普通用户无法控制物理路径。
- 项目只能落在目标 PC 的 `<受管项目根目录>/projects/{username}` 下。
- 管理员可以使用合法的任意本机目录。
- 目录穿越、符号链接逃逸、重复路径和危险根目录被拒绝。
- 取消注册不删除文件。

### 阶段 6：统一项目可见性

工作：

- 在项目解析和数据库执行入口接入可见性检查。
- 项目列表、REST、WebSocket、文件和搜索复用检查。

验证：

- 无权用户无法通过直接 `project_id`、WebSocket 订阅或文件地址访问项目。
- 用户只看见自己拥有或获分享的项目。
- 管理员可查看全部平台注册项目。
- 移除可见关系后，已有订阅立即停止接收项目事件。

### 阶段 7：消息作者完整性

工作：

- 扩充消息字段和迁移。
- 收拢任务消息与助手聊天消息持久化入口。
- 前端统一展示作者。

验证：

- 所有用户、助手、系统和定时消息的作者字段均非空。
- 平台消息记录登录用户名快照。
- 本地消息记录本地用户名快照。
- 后台回复能追溯原始发起人。
- 历史缺失作者显示“历史用户”，不被错误回填。

### 阶段 8：任务动作审计

工作：

- 建立统一审计服务。
- 接入任务生命周期、审核、定时器和项目成员变化。

验证：

- 启动、暂停、恢复、停止和取消均能查到操作者。
- 后台恢复和定时任务包含 `actor_type` 与原始发起人。
- 失败和拒绝操作也有结果记录。
- 审计元数据不包含敏感值。

### 阶段 9：认证和注册页面

工作：

- 实现初始化、注册、登录和等待审核页面。
- 增加路由守卫与登录后返回。

验证：

- 各平台状态跳转准确。
- 表单校验、焦点和加载状态符合规范。
- 注册关闭、待审核、禁用和数据库故障均有清晰页面。

### 阶段 10：管理中心

工作：

- 管理概览。
- 用户管理。
- PC、连接状态和用户-PC 分配管理。
- 供应商、分配、设备同步状态和 Token 用量管理。
- 项目管理和管理员外部目录选择。
- 操作记录。
- 平台设置。

验证：

- 普通用户看不到且无法打开管理功能。
- 普通用户只能看到分配给自己的 PC，管理员能查看全部 PC 和连接历史。
- 从设备列表打开 PC 后，页面所有 HTTP 与 WebSocket 请求均保持在同一设备作用域。
- 管理操作有确认、错误恢复和审计。
- 页面模块测试覆盖自己的状态、请求和校验。
- 大列表具备分页或服务端筛选，避免一次加载全部记录。

### 阶段 11：项目成员与现有功能回归

工作：

- 项目设置增加“成员”页签。
- 明确区分平台成员、公开任务分享和远程设备访问。
- 完成模式切换和权限变化的实时处理。

验证：

- 项目所有者能分享自己的项目。
- 管理员共享项目仅管理员能修改成员。
- 现有任务、画布、聊天、助手、计划任务、远程项目和公开分享无回归。
- i18n 所有词典键一致且非空。

## 12. 完成标准

- 平台模式可即时启停，无需重启。
- 平台主数据库始终为 `<网关平台根目录>/workstep_platform.db`。
- PC 能通过配置网关地址主动连接，网关能显示在线状态和用户分配关系。
- 管理员能多选 PC 批量执行受支持的引擎管理动作，并逐台查看进度、结果和重试失败项。
- 网关能集中维护供应商、模型和价格，并只向授权用户与 PC 下发配置。
- 平台供应商密钥默认保留在网关；确需下发时使用设备加密凭据且不落入普通配置、日志或审计。
- 每台 PC 的供应商期望版本、应用版本、同步状态和撤销状态可追踪。
- Token 用量按用户、PC、项目、供应商和模型汇总，远程项目与重试不会重复计数。
- 已分配用户可从网关完整代理访问目标 PC 的 WorkStep HTTP 与 WebSocket 界面。
- 普通用户项目只能创建在目标 PC 的 `<受管项目根目录>/projects/{username}/`。
- 管理员共享项目可以使用任意通过安全校验的本机绝对目录。
- 项目默认私有，所有者可以分享，管理员可以管理全部项目可见用户。
- 用户不能通过项目 ID、WebSocket、搜索或文件接口看到无权项目。
- 本地模式和平台模式下，每条新消息都有明确作者用户名或系统身份。
- 所有助手和后台消息都能追溯原始发起人。
- 任务启动、暂停、恢复、停止和取消均有持久化操作者记录。
- 关闭平台模式不会删除平台数据或项目文件。
- 全部新增 Peewee 异步路径通过专用数据库执行器运行，并有事件循环非阻塞回归测试。
- 前端管理页面符合现有组件复用、弹框关闭保护、加载旋转和 i18n 规范。

## 13. 第一版暂不包含

- 组织、部门和用户组。
- `viewer/editor` 等项目细粒度角色。
- 单独的接口权限编排系统。
- 邮件注册验证和邮件找回密码。
- OAuth、LDAP、OIDC 等外部身份源。
- 用户磁盘或任务配额。
- 自动迁移不同平台根目录之间的数据。
- 自动移动管理员注册的外部项目目录。
