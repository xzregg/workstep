# 对话级定时消息

状态：已按确认原型实现；相关后端 367 项、前端 45 项测试及前端构建通过。渠道发送使用模拟平台验证，未进行真实群发。

原型：`prototypes/conversation-schedules.html`。

视觉以当前 `SchedulePage`、`ScheduleCenter`、`TaskScheduleEditor`、`ScheduleRuleEditor` 及对应 CSS 为基础：保留左侧周期性/一次性列表与类型筛选、中间配置、右侧运行记录及可拖分隔线。执行频率保持现有「周期 / 按间隔 / 单次」和生效日期范围。只新增「对话」目标及其会话选择、消息与自动回传说明，不重新设计整个定时页面。

## 范围

项目内定时入口与外层设置上方的定时入口统一复用现有 SchedulePage，执行类型固定为「创建任务 / 协调任务 / 对话」。只新增「对话」选项，不在对话窗口增加入口、按钮或配置侧栏。外层入口继续由 ScheduleCenter 提供项目切换；项目内入口沿用当前项目。选择「对话」后列出当前项目未归档的普通会话和渠道会话。

定时内容是发给助手的用户消息：到期写入指定对话，使用该对话上下文和执行配置完成一轮回复。用户已补充自然语言创建场景：在对话里说“两小时后帮我看一下情况怎么样”，助手通过 CLI 创建该对话的一次性定时任务。

## 表单与投递

名称、消息正文、重复规则和时间；复用已有定时规则能力，原型展示每天、工作日、每周和单次。沿用当前时区。在配置页显式选择目标会话；会话选项标注普通对话或渠道平台。项目范围由现有页面确定，不额外选择流程或任务。

普通对话：消息与回复留在当前对话。
渠道对话：固定显示机器人、平台、群或私聊来源，助手最终回复自动回传同一渠道目标，不提供其他渠道选择，也不修改默认项目或群任务绑定。不重复使用通用计划通知发送第二份回复。

列表提供编辑、暂停、恢复、删除。消息流标注定时来源，完成后显示渠道投递状态；渠道投递失败只重试投递，不重新执行助手。

## CLI 与对话中的自然语言创建

复用现有 `schedule create/update/list/pause/resume/delete` 和统一工具注册/API，新增 `--target session`、`--session <WorkStep会话ID>`；复用 `--instruction` 作为对话消息内容。现有 `--notify-session` 仅表示通知收件目标，不能与执行目标 `--session` 混用。

新增一次性相对时间 `--after 2h`（支持明确单位，如 `30m`、`2h`），与 `--at`、`--cron`、`--every-minutes` 互斥。相对时长由 daemon 受理时的权威时钟计算，并持久化为绝对单次执行时间；CLI 返回具体时间和时区。`--after 2h` 表示两小时后执行一次，不等同于每两小时执行。绝对日期继续支持现有 `--at`。

命令示例（尖括号是上下文占位）：

```sh
workstep schedule create \
  --project <当前项目ID> \
  --target session \
  --session <当前WorkStep会话ID> \
  --name "两小时后检查进展" \
  --instruction "检查我们刚才讨论事项的最新进展，说明变化、未完成事项和需要我处理的问题。" \
  --after 2h \
  --timezone Asia/Shanghai \
  --json
```

当前项目和 WorkStep 会话 ID 由运行时系统上下文提供；普通对话与渠道对话都必须注入，不能让模型从目录、标题或最近会话猜测。WorkStep 会话 ID 与外部群 ID、引擎 session/thread ID 不同。外部终端调用必须显式指定项目及会话，后端校验会话属于项目、未归档且调用者有相应权限。

助手把用户的延迟请求转换成“到时实际要执行的消息”，保留具体事项的引用，不把“两小时后再提醒我”原样作为到时指令，避免递归创建定时任务。上下文不能确定“情况”指什么时才补问。创建成功后告知实际执行时间和目标对话；只有后端返回成功才能声称已安排。

创建请求应携带源消息/工具调用的稳定幂等标识，网络重试返回原规则，不重复创建，也不重新起算两小时。定时触发本身不得被解释为再次安排同样规则。

CLI 创建的规则立即出现在同一项目的统一定时配置页面「对话」类型中，和界面创建规则共用编辑、暂停、删除与生命周期清理。渠道对话自动回传原机器人及原群/私聊，CLI 不需要额外传通知机器人。

验证覆盖普通/渠道当前会话定位、相对时间跨日与单次语义、绝对时间及时区、重复请求幂等、跨项目/归档会话拒绝、触发不递归安排、界面可见，以及删除/归档清理。

## 生命周期与边界

- 对话删除或归档：清除全部关联规则、撤销待触发和排队执行。批量操作使用同一清理入口。沿用现有运行中会话的删除／归档保护，成功操作时同事务清理。
- 恢复归档：仅恢复对话，不恢复规则。渠道下一条消息新建的会话不继承旧规则。
- 正在执行的定时回合：请求停止该回合，终态投递前复核会话仍有效；不停止同对话中的人工回合。已发出的外部消息无法撤回。
- 同一对话已有执行时：等待当前回合结束后串行处理，同一规则不重复积压。后台恢复不集中补发离线期间多次错过的消息。
- 渠道失效、机器人停用或路由已重置：显示投递失败，不改发其他渠道或新会话。群绑定任务后，旧渠道对话的定时规则标为失效并提示绑定变化，避免与任务对话并行处理同一群；解除绑定后由用户恢复。
- 普通消息清空与对话删除不同：仅清消息保留会话时，规则是否保留在实施前按实际产品入口明确，不把清消息暗中等同于删除对话。

## 实施结构

扩展既有 Schedule 的对话目标类型与 session_id，复用调度规则、发生记录、暂停及重试。执行通过普通／渠道对话共用 AssistantRuntime 接入，保留 channel 分流，禁止复制聊天运行时。归档、单删、批删及项目删除统一调用生命周期清理。所有 Peewee 工作在项目数据库执行器内完成。

前端新增 ConversationScheduleEditor 自管理模块，由 SchedulePage 的「对话」类型分支装配；ChatPage 不改动。编辑器复用已有定时规则表单、列表和运行记录，渠道回传复用既有会话回复发送机制。实现时补 API、后台触发、执行取消、归档清理与慢数据库响应性测试，同步 code-map；手册在本批合并交付节点更新。
