# Gateway 平台模式逐阶段开发计划

> 状态：阶段 0、1 已实现，其余阶段待开发。本文把 [平台模式总体方案](./platform-mode.md) 的实施阶段细化为可交付的开发批次；产品规则、数据模型和页面设计以总体方案为准。目标分支：`feat/platform-gateway-v1`。

## 执行约束与交付方式

- 每阶段先写失败的行为测试，再实现，再完成本阶段回归；阶段完成后独立提交。一个阶段内可拆多次提交，但不能把未通过验收的阶段标成完成。
- `apps/gateway` 是独立 Python/FastAPI 服务；平台门户和管理后台位于独立 `apps/gateway-web`；`apps/daemon` 只增加受管设备客户端与必要的本机服务门禁；`apps/desktop` 处理登录回调。两端只共享版本化协议定义，不互相导入业务模块。
- Gateway 首版单实例、SQLite 默认；保留 PostgreSQL 数据层兼容测试。PC 保留每项目 `.workstep/workstep.db`。Gateway 不读取项目数据库，也不规定本机项目目录。
- PC 主动建立常驻控制 WSS；仅远程访问时建立按需数据 WSS。直接打开本机客户端时，认证后业务 HTTP/WebSocket 走 loopback。
- 项目发布与项目授权独立于整台 PC 授权。管理员可将已发布项目授予用户或用户组 `read/edit`；`task.create` 是单独的能力门禁。
- 阶段间共享验收基线：本地模式不回归；新增异步数据库、文件、网络和 SDK 路径有慢 I/O 健康检查 canary；Peewee 工作单元进入项目数据库执行器；Web 功能更新 `docs/code-map.md` 与行为测试。

## 依赖与里程碑

| 批次 | 前置阶段 | 形成的可演示能力 |
|---|---|---|
| 0—2 | 无 → 0 → 1 → 2 | 独立网关、数据库、用户和企业身份 |
| 3A—3C | 2 → 3A → 3B → 3C | 受管 PC 登录、在线连接、门户远程操作 |
| 4A—4C | 3B → 4A → 4B → 4C | 供应商下发、批量设备命令、Token 统计 |
| 4D—6 | 3C、4A → 4D → 5 → 6 | 组 Skills、项目发布授权与访问隔离 |
| 7—8 | 3A、5 → 7 → 8 | 完整消息身份与操作审计 |
| 9—11 | 所有对应后端能力 → 9 → 10 → 11 | 用户页面、管理后台、分享及发布验收 |

阶段 2 的 Gateway 身份 API 和阶段 3A 的桌面授权 API 可以在阶段 9 页面完成前用测试客户端验证。阶段 4D 的用户组是阶段 5 组授权的前置，不能留到项目授权之后才建。

编号对应关系：本文 3A—3C 细化总体方案的阶段 3；4A—4C 细化总体方案的阶段 4；本文 4D 对应总体方案的“阶段 4B：用户组与项目 Skills”。执行和阶段记录以本文编号为准。

## 阶段 0：独立应用与协议骨架

交付物：可单独启动、测试和构建的 Gateway、Gateway Web，以及唯一的共享协议包。

开发顺序：

1. 新建 `apps/gateway` 的 FastAPI lifespan、配置读取、健康检查、统一错误响应和测试夹具；建立 `apps/gateway-web` 的 React/Vite/TypeScript 路由骨架。Gateway 可托管前端构建产物，前端开发服务器独立运行。
2. 在 `packages/gateway-protocol` 定义协议版本、能力声明、控制消息 envelope、错误码、代理流标识与帧类型；生成或校验两端使用的 schema，避免 Gateway 与 daemon 分别维护副本。
3. 在 daemon 建立独立 `services/gateway_client/` 包和未启用的生命周期挂钩；普通安装未携带受管配置时不连接网关。
4. CI 增加 Gateway 单测、Gateway Web 测试/构建、协议 schema 兼容检查；文档写明独立部署和端口/域名配置。

接口边界：Gateway 不导入 daemon 的 Peewee 模型、任务服务或引擎；daemon 不导入 Gateway 用户、会话或 SQLAlchemy 模型。协议层只有序列化模型，不执行设备命令。

测试与验收：健康检查与优雅关闭通过；未知必需协议版本被拒绝；未配置 Gateway 时现有 daemon 启停及 API/WebSocket 测试保持通过；新增路径标注在 `docs/code-map.md`。完成后提交骨架与协议基线。

阶段 0 交付记录（2026-09-28）：已建立独立 Gateway 服务与门户、共享协议模型及固定 schema、daemon 未配置时的生命周期挂钩；接口为 `/api/health`，无数据库迁移。Gateway/协议 8 项测试、daemon 生命周期相关 14 项测试、门户测试与构建均通过，协议 schema 校验通过。此阶段没有新增阻塞 I/O 路径，因此慢 I/O canary 不适用。阶段 1 的数据库、配置签名和受管连接尚未开始。回滚方式：撤销本阶段提交；普通 daemon 的本地服务不依赖 Gateway 在线状态。

## 阶段 1：Gateway 数据库与受管配置

交付物：可迁移、可备份的 Gateway 数据库，以及 PC 侧可验证的受管配置读取。

开发顺序：

1. 用 SQLAlchemy 异步接口和 Alembic 建立表与索引；首版 SQLite 数据文件默认位于 Gateway 数据目录，`database_url` 可配置 PostgreSQL。迁移按实体分组，并提供空库初始化和已有库升级测试。
2. 先建立平台设置、用户/会话、设备/连接、项目/授权、供应商、用量、审计和作业所需的最小表；业务阶段再补字段和索引，避免一次性实现全部 repository。
3. Gateway 启动时校验迁移版本、数据库可用性和单实例约束；失败返回明确故障状态，不自动退回其他数据库。
4. 受管包配置固定 Gateway ID、地址和公钥 pin；daemon/desktop 读取并验证签名，不在普通设置页提供修改入口。受管配置与普通本地配置分离。

接口边界：数据库连接串只经部署配置传入；管理 API 只暴露后端类型、脱敏地址、健康与迁移版本。数据库后端切换必须离线备份/迁移，不在运行中热切换。

测试与验收：SQLite 冷启动、重复迁移、事务回滚、唯一约束通过；PostgreSQL 跑迁移和核心事务兼容测试；SQLite 锁竞争和慢盘下健康检查仍及时响应；配置损坏或签名不符时受管客户端拒绝连接，不破坏本地项目。

阶段 1 交付记录（2026-09-28）：实现分组 Alembic 迁移、异步数据库访问、SQLite 在线备份、SQLite/PostgreSQL 单实例约束、脱敏数据库状态摘要与受管包签名配置。迁移文件已确认进入 Gateway wheel；macOS 的受管桌面包已实际构建，成品中 Desktop 与随包 Python 均成功验签，Windows 打包留待发布阶段复核。Gateway/协议测试、daemon 生命周期和配置测试、Desktop 测试及构建脚本测试通过；PostgreSQL 17 临时容器的迁移与事务测试通过；SQLite 写锁和慢备份下健康检查及时响应。无管理登录前，数据库状态只保留在服务内部，阶段 2 之后再通过受权管理 API 暴露。回滚方式：撤销本阶段提交；阶段 0 的独立服务骨架仍可运行。

## 阶段 2：Gateway 用户、管理员与企业身份

阶段 2 进行中（2026-09-28）：本地账号、注册三模式、首位管理员与恢复管理员、Argon2id 密码、摘要会话、安全 Cookie/CSRF、管理员审核/禁用/重置、短时密码二次认证、平台/部门范围的身份管理员已实现并通过 Gateway API 与迁移回归。钉钉/企微扫码适配器、稳定 subject 映射、显式绑定、防重放、跨租户校验、管理员目录快照/幂等事件导入、连接器主动拉取与定时对账已有模拟 HTTP 与 API 回归。第三方事件回调验签及门户页面仍待完成，本阶段尚未验收。

交付物：Gateway 自有用户体系及可选钉钉、企业微信身份接入。

开发顺序：

1. 实现仅空平台可用的首位超级管理员初始化；建立保底恢复管理员、最后一名超级管理员保护、管理员作用域与二次认证入口。
2. 实现开放注册、注册后审核、关闭注册、管理员建号、用户名密码登录、注销、改密、禁用与重置。密码自适应哈希；服务端会话只保存 token 摘要，浏览器使用安全 Cookie 和 CSRF 防护。
3. 把钉钉/企业微信做成 Gateway 的独立身份连接器：扫码 state/nonce、服务端换票、稳定外部 subject、已登录用户显式绑定。可变姓名只作展示名和用户名候选。
4. 实现第三方部门及人员全量同步、变更事件幂等应用和定时对账；外部组织投影只读，Gateway 本地账户状态、管理角色和授权关系由 Gateway 维护。
5. 关闭自注册时禁止扫码即时建号；扫码只匹配预同步或管理员创建且已绑定的 Gateway 用户。

接口边界：身份/组织 API 使用 `Gateway user_id` 为主键；外部唯一键是身份源、企业/租户与稳定 subject 的组合。现有 daemon 企业微信/钉钉机器人功能不作为登录连接器复用。

测试与验收：注册三模式、待审核、禁用、会话过期、登出、密码重置和最后管理员保护通过；扫码回调重放、跨租户、同名、中文姓名、改名和未同步用户被正确处理；停用第三方连接器不影响 Gateway 密码登录。

## 阶段 3A：Desktop 授权与设备注册

阶段 3A 进行中（2026-09-28）：Gateway 已实现短期单次 code、PKCE/state/nonce/网关与安装实例绑定、设备公钥登记及审批、停用/撤销、旧密钥证明后轮换、短期 Ed25519 设备授权；API/数据库与签名重启稳定性回归通过。Desktop 主进程已接入系统浏览器、协议回调、固定网关兑换和安全存储；Gateway Web 桌面登录页支持本地密码及第三方扫码回跳，`/admin/devices` 支持超级管理员二次认证后管理设备；daemon 已实现签名设备授权及私钥证明校验、本机会话和受管 HTTP/WebSocket 守卫。统一安装包目录、公开下载 API 与 `/devices/empty` 页面已实现，慢文件复制健康检查通过。本机会话失效专用标记、桌面端单飞重认证及受管请求 Origin 检查通过单元回归；实际安装包端到端验收尚未完成。

交付物：统一受管安装包可让当前用户登录并登记当前 PC。

开发顺序：

1. Desktop 生成 `state`、`nonce`、PKCE 和 `app_instance_id`，用系统浏览器打开固定 Gateway 的桌面登录入口；扩展现有 `workstep://` 路由处理 `auth/callback`，处理多开和重复回调。
2. Gateway 签发短期单次 authorization code；Desktop 用 PKCE 兑换用户与设备作用域会话。自定义协议 URL 仅包含 code 与 state。
3. PC 首次绑定生成设备密钥，Gateway 登记设备公钥、版本和绑定用户；管理侧可审批、停用、撤销与轮换设备身份。
4. daemon 建立 Gateway 派生的本机会话，将用户 ID、用户名及权限快照映射为统一当前操作者；本机 Web/API/业务 WebSocket 均要求该会话。
5. 登录成功后 Desktop 打开 loopback 工作台；下载页对所有用户提供同一网关受管包及校验信息。

测试与验收：code 过期、重放、错误 PKCE/state/app_instance_id 或错误网关均失败；登录后本机业务请求不经 Gateway 代理；无本机会话不能访问受管 API；关闭/最小化桌面窗口与完全退出 daemon 的设备状态区分准确。

## 阶段 3B：常驻控制连接与策略

阶段 3B 进行中（2026-09-28）：Gateway 端已实现新鲜挑战与受设备密钥委托的临时控制密钥证明、设备/用户状态核验、单设备在线连接与历史、心跳超时及停用/撤销主动断开；daemon 在受管登录后主动连接，心跳与退避重连，授权失效时 Desktop 可重新登录。签名消息、策略 TTL 和命令仍待实现。

交付物：PC 在线状态、策略变更和结构化命令可可靠传输。

开发顺序：

1. daemon 在 lifespan 启动出站控制 WSS，完成设备握手、能力协商、心跳、指数退避重连和关闭；Gateway 维护单设备活动连接与连接历史。
2. 控制消息涵盖策略 revision、供应商/Skills 配置清单、命令、用量与审计批次、回执、撤销通知；消息带类型、版本、ID、设备目标和过期时间。
3. 在 daemon 统一验证 Gateway 签名、设备 ID、过期时间、消息 schema 和幂等 ID；业务动作经现有应用服务执行。
4. 平台用户/设备授权变化发布新签名策略快照；断线期间按明确的快照 TTL 运行，过期后新的受管操作拒绝。

测试与验收：NAT 后设备主动连通；断线重连不重复执行命令；设备被撤销后不能重新握手；健康检查不受慢握手、慢配置和断线重试影响；已启动任务不因控制连接断开而中断。

## 阶段 3C：按需数据连接与整机远程代理

交付物：用户在 Gateway 门户打开获整机授权的 PC，得到完整 WorkStep Web 界面。

开发顺序：

1. Gateway 校验 `user_devices` 整机访问关系，签发短期设备会话票据；浏览器经设备独立子域 `d-<opaque-device-id>.<gateway-domain>` 访问，部署提供通配符 DNS/TLS。
2. Gateway 经控制 WSS 通知 PC 建立按需数据 WSS；数据帧以 `stream_id` 多路复用 HTTP、业务 WebSocket、上传、下载、取消及流控。
3. PC 侧 ASGI bridge 把可信代理请求送入现有 FastAPI 应用，注入经过校验的当前操作者和设备作用域，不向本机 loopback 再发 HTTP。
4. Gateway 处理 Host/Origin、Cookie、Location、WebSocket upgrade、流式响应、超时、背压和会话关闭；门户加入远程 PC 上下文提示条。
5. 与 Electron 原生操作相关的按钮在远程浏览器中明确降级，不提供任意宿主文件系统或桌面控制能力。

测试与验收：无整机授权不能进入；不同设备子域的 Cookie 和票据不能互用；根路径 `/api`、`/ws` 和静态资源正确路由；流式响应、大文件及业务双向 WebSocket 不截断；设备离线和权限撤销关闭代理流；慢数据连接不阻塞控制心跳。

## 阶段 4A：供应商控制面与配置落地

交付物：管理员配置供应商后，获授权 PC 可使用现有本机供应商加载链。

开发顺序：

1. Gateway 保存供应商、模型目录、价格版本、用户/设备分配、期望配置 revision 和应用状态。
2. 控制 WSS 下发签名的期望清单与配置包；PC 校验后原子写入现有配置位置，调用现有 reload、测试和调用服务，回传已应用版本或错误。
3. 在 daemon 的供应商服务层标记 `managed` 项并拒绝用户通过 UI、REST 或导入入口新增、修改、删除和覆盖。额外本地供应商首版默认关闭。
4. 删除、撤销、轮换通过 tombstone 同步；冲突或落盘失败保留上一可用版本并显示风险状态。

测试与验收：错误签名、旧版本和未授权用户/设备被拒绝；重连与重复下发幂等；模型请求从 PC 直接发送到供应商；密钥不进入普通 API、日志、审计或项目数据库。已下发密钥可以由拥有本机系统文件权限的人读取，这不是 Gateway 的保密边界。

## 阶段 4B：批量设备命令

交付物：管理员对多台 PC 批量执行已支持的引擎管理动作，并能逐台查看结果。

开发顺序：

1. 从本机引擎安装路由抽取共享应用服务；本机点击和 Gateway 控制命令调用同一服务及互斥逻辑。
2. Gateway 创建批量作业，提交时冻结设备目标、引擎版本、参数和并发数；每台 PC 生成独立命令 ID、幂等键、TTL 和状态。
3. PC 命令执行器只支持版本化目录里的 `install/update/rollback/refresh/test` 等结构化动作，不接收任意 shell 或 URL。
4. 控制 WSS 回报已接收、运行中、成功/失败；离线重试遵守明确 TTL，管理员可只重试失败设备。

测试与验收：并发数为 1 时严格逐台执行；单设备失败不阻塞剩余目标；重发不重复安装；离线过期命令不在重连后突发执行；未知动作、越权目标和错误参数被 PC 拒绝。

## 阶段 4C：Token 用量与成本账本

交付物：按人、PC、项目、供应商和模型查询 Token 及估算成本。

开发顺序：

1. 从现有标准化 usage 事件生成全局 `usage_event_id`、原始发起人、执行设备、任务/会话、模型、Token 分类和价格版本快照。
2. PC 将事件先写本地持久化 outbox；控制 WSS 批量上传，Gateway 按事件 ID 幂等写入并返回逐批回执，PC 收到回执后清理。
3. Gateway 统计 API 提供时间范围、用户、PC、项目、供应商和模型维度，以及未完成计量、供应商账单对账差异状态。
4. SQLite 使用有界批次与短事务；写入压力不能压住登录、心跳或健康检查。

测试与验收：断网重发和重复批次只计数一次；浏览器与代理层不二次计量；缺失 usage 不静默记零；Token 和成本对照现有本地报表；慢数据库、慢供应商 SDK 下事件循环 canary 通过。

## 阶段 4D：用户组与项目 Skills

交付物：组长可为本组关联项目分配平台审核的 Skill 固定版本。

开发顺序：

1. 建立手工组、部门映射组、成员、组长和组项目关系；`policy_only` 项目仅参与 Skills 策略，不获得远程访问权。
2. Gateway 保存 Skill 包、不可变版本、摘要、审核、组授权和项目期望 revision；组长只能选择本组获授权的版本。
3. PC 校验签名、摘要、大小、路径和符号链接，原子写入项目 `.workstep/skills/` 与 manifest，再触发现有 Skill Center 扫描。
4. 更新、撤销和冲突回报可追踪；运行中的任务不热切换 Skill。

测试与验收：组长不能读取项目内容或修改其他组；组项目关系不自动成为远程项目授权；未审核包、路径穿越、同名非受管文件和摘要错误安全失败；重复同步幂等；撤销仅删除对应受管副本。

## 阶段 5：远程项目发布、组授权与任务能力

交付物：管理员可将发布项目授予用户/组，受权用户可从 Gateway 门户直接打开项目。

开发顺序：

1. PC 明确发布项目 ID、名称和设备 ID；Gateway 记录 `remote_published`，不保存宿主机绝对路径。取消发布只撤销登记。
2. 管理员创建/撤销 `project_access_grants`：主体为用户或组，级别为 `read/edit`。用户有效级别取直接授权与当前有效组授权的并集。
3. Gateway 为项目入口签发绑定用户、设备、项目和级别的短期票据；项目授权无须整机访问关系。
4. 增加 `task.create` 用户/设备/项目范围能力；本机和远程任务创建均进入 daemon 的统一服务门禁。`edit` 本身不隐含 `task.create`。

测试与验收：未发布项目不可枚举；只有项目授权的用户不能打开完整 PC；`read` 不可修改；组成员移除实时失权；无 `task.create` 不能创建任务；取消发布不删本机项目文件。

## 阶段 6：远程项目跨接口隔离

交付物：单项目远程票据在所有项目读写入口都只能访问目标项目。

开发顺序：

1. 在 Gateway 票据签发和 daemon 项目解析层建立统一项目作用域，避免每个路由自行拼接授权判断。
2. 将任务、聊天、流程、助手、搜索、统计、上传、下载、产物、Markdown 图片和业务 WebSocket 订阅纳入作用域检查。
3. `read` 请求保持只读；编辑、任务状态改变和消息发送要求 `edit`，任务创建额外要求 `task.create`。
4. 账户禁用、组成员变化、授权撤销、设备离线时取消现有项目代理流及事件订阅。

测试与验收：直接猜 `project_id`、文件路径、搜索参数、WebSocket channel 或跨设备票据均无法越权；管理员管理 scope 不自动授予项目内容读取；读取和写入 API 均有正反例；已有订阅在权限撤销后停止。

## 阶段 7：全消息作者和后台发起人

交付物：新消息必有作者身份快照，后台行为能追溯原始发起人。

开发顺序：

1. 给项目消息和独立聊天消息迁移 `author_username/author_name/author_type/initiated_by_*` 等字段；已有行不伪造为当前用户。
2. 统一用户、助手、系统、定时器和人工审核消息持久化入口，由当前操作者服务生成快照。
3. 启动任务时将用户身份存入运行记录，后台续跑、服务恢复和定时触发按运行记录恢复 `initiated_by`。
4. Web 消息元数据显示当时展示名和用户名，历史缺失作者显示“历史用户”。

测试与验收：任务阶段、协调助手、流程助手、任务创建助手、独立聊天、运行中插入和系统可见消息逐类覆盖；本地和平台模式均无新空作者；服务重启后发起人不丢；慢项目数据库 canary 通过。

## 阶段 8：任务与平台操作审计

交付物：可查询、不可被普通用户修改的操作记录。

开发顺序：

1. Gateway 对登录、用户/组/管理员、项目授权、供应商、批量命令和分享操作追加结构化审计。
2. PC 在任务启动、排队、暂停、恢复、停止、取消、阶段控制、人工审核、定时触发和系统恢复时写本地 audit 及 outbox。
3. 受管模式通过控制 WSS 以 `audit_event_id` 幂等上传；本地模式保留本地审计查询。
4. 记录操作者、发起人、运行模式、设备、项目、任务、动作、结果、时间和有上限的脱敏元数据。

测试与验收：成功、拒绝和失败均留痕；断线补传不重不漏；任务动作发生时审计写入与业务状态一致；审计不记录正文、密码、令牌、供应商 Key；管理员查询遵守管理 scope。

## 阶段 9：注册、登录与员工工作台页面

交付物：用户完成平台注册、桌面登录和门户工作台的完整交互。

开发顺序：

1. Gateway Web 实现首位管理员初始化、Gateway 账号注册/登录、钉钉/企业微信扫码、审核等待、禁用与错误恢复。
2. 无 PC 时展示统一安装包、平台地址、版本与校验值；设备上线后自动进入“我的 PC”。
3. 工作台展示“我的 PC”“我的项目”和个人账户；整机入口与单项目入口分开，项目卡片说明宿主 PC、授权来源和 `read/edit`。
4. Desktop 显示登录请求、浏览器返回、code 兑换、失败重试和退出；Gateway 管理员登录后默认仍在工作台，可切换管理后台。

测试与验收：注册开关与页面行为一致；扫码过期、取消和身份源故障可恢复；登录失效后回到原目标；无 PC 用户仍可查看项目授权列表和下载安装入口；移动端 320/390/1023px 核对布局与点击区域。

## 阶段 10：Gateway 管理后台

交付物：管理员在同一 Gateway 会话内管理用户、组织、PC、项目和平台策略。

开发顺序：

1. 建管理布局与工作台/后台切换；所有列表使用服务端过滤、排序和分页，API 按角色和 scope 强制校验。
2. 依次落地概览、用户与组织同步、管理员权限、设备与批量作业、项目访问授权、供应商与应用状态、用户组与 Skills、用量、审计、平台设置。
3. 将每个有独立异步请求、校验和确认的弹框或侧栏抽为自管理模块；危险操作使用 `ConfirmDialog`，不使用原生 `alert/confirm`。
4. 管理页面展示连接在线与 daemon 健康的区别；项目列表只含已发布元数据，管理角色不自动提供内容入口。

测试与验收：普通用户直调管理 API 返回拒绝；部门/设备管理员越 scope 被拒绝；批量目标在提交时冻结；长列表分页；加载错误恢复、表单校验和关闭保护由模块测试覆盖；更新 `docs/code-map.md`。

## 阶段 11：平台分享、受管隔离与发布门禁

交付物：可部署的 Gateway V1，并与现有本地点对点远程项目保持隔离。

开发顺序：

1. 新平台任务分享由 Gateway 创建公开 URL、密码/过期/访问会话，并给 PC 签发绑定分享、设备、项目、任务和模式的内部票据。
2. 受管模式在前后端禁用旧远程项目分享串、导入和 daemon 直出公开任务分享；本地模式继续保留旧入口与凭据。
3. 完成设备撤销、解绑、离线、客户端版本不兼容、Gateway 数据库不可用时的故障页面及审计。
4. 增加 Gateway 部署、通配符 DNS/TLS、数据库备份恢复、密钥轮换、客户端发布与回滚文档。
5. 跑端到端链路与容量基准：注册 → PC 绑定 → 本机使用 → 门户访问 PC → 项目组授权 → 任务 → 用量/审计 → 撤销。

测试与验收：公开分享可按 `read_only/interactive` 使用、撤销和过期；宿主 PC 离线不泄露直连地址；旧分享凭据不能用于 Gateway；daemon、Gateway、Web、Gateway Web、Desktop 的相关测试和构建均通过；代理并发、文件流、SQLite 锁竞争和控制心跳基准有记录。
