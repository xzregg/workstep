## 执行约束与交付方式

剩余工作按 [九批次开发与验收计划](platform-gateway-remaining-development.md) 收敛。批次 9 已启动 `http://localhost:8700` 本机网关；允许回环 HTTP，Gateway、Desktop、daemon 与受管包保持统一地址校验，企业微信／钉钉真实跳转仍暂缓。仅本机服务与相关自动化检查通过，不据此认定阶段 11 或批次 9 整体完成。

- 每阶段先写失败的行为测试，再实现，再完成本阶段回归；阶段完成后独立提交。一个阶段内可拆多次提交，但不能把未通过验收的阶段标成完成。
- `apps/gateway` 是独立 Python/FastAPI 服务；平台门户和管理后台位于独立 `apps/gateway-web`；`apps/daemon` 只增加受管设备客户端与必要的本机服务门禁；`apps/desktop` 处理登录回调。两端只共享版本化协议定义，不互相导入业务模块。
- Gateway 首版单实例、SQLite 默认；保留 PostgreSQL 数据层兼容测试。PC 保留每项目 `.workstep/workstep.db`。Gateway 不读取项目数据库，也不规定本机项目目录。
- PC 主动建立常驻控制 WSS；仅远程访问时建立按需数据 WSS。直接打开本机客户端时，认证后业务 HTTP/WebSocket 走 loopback。
- 项目发布与项目授权独立于整台 PC 授权。管理员可将已发布项目授予用户或用户组 `read/edit`；`task.create` 是单独的能力门禁。
- 阶段间共享验收基线：本地模式不回归；新增异步数据库、文件、网络和 SDK 路径有慢 I/O 健康检查 canary；Peewee 工作单元进入项目数据库执行器；Web 功能更新 `docs/code-map.md` 与行为测试。

## 阶段 0：独立应用与协议骨架

交付物：可单独启动、测试和构建的 Gateway、Gateway Web，以及唯一的共享协议包。

开发顺序：

1. 新建 `apps/gateway` 的 FastAPI lifespan、配置读取、健康检查、统一错误响应和测试夹具；建立 `apps/gateway-web` 的 React/Vite/TypeScript 路由骨架。Gateway 可托管前端构建产物，前端开发服务器独立运行。
2. 在 `packages/gateway-protocol` 定义协议版本、能力声明、控制消息 envelope、错误码、代理流标识与帧类型；生成或校验两端使用的 schema，避免 Gateway 与 daemon 分别维护副本。
3. 在 daemon 建立独立 `services/gateway_client/` 包和未启用的生命周期挂钩；普通安装未携带受管配置时不连接网关。
4. CI 增加 Gateway 单测、Gateway Web 测试/构建、协议 schema 兼容检查；文档写明独立部署和端口/域名配置。

接口边界：Gateway 不导入 daemon 的 Peewee 模型、任务服务或引擎；daemon 不导入 Gateway 用户、会话或 SQLAlchemy 模型。协议层只有序列化模型，不执行设备命令。

测试与验收：健康检查与优雅关闭通过；未知必需协议版本被拒绝；未配置 Gateway 时现有 daemon 启停及 API/WebSocket 测试保持通过；新增路径标注在 `docs/code-map.md`。完成后提交骨架与协议基线。

阶段 0 交付记录（2026-09-28）：已建立独立 Gateway 服务与门户、共享协议模型及固定 schema、daemon 未配置时的生命周期挂钩；接口为 `/api/health`，无数据库迁移。Gateway/协议 8 项测试、daemon 生命周期相关 14 项测试、门户测试与构建均通过，协议 schema 校验通过。此阶段没有新增阻塞 I/O 路径，因此慢 I/O canary 不适用。阶段 1 的数据库、配置签名和受管连接尚未开始。回滚方式：撤销本阶段提交；普通 daemon 的本地服务不依赖 Gateway 在线状态。

## 阶段 1：Gateway 数据库与受管配置

交付物：可迁移、可备份的 Gateway 数据库，以及 PC 侧可验证的受管配置读取。

开发顺序：

1. 用 SQLAlchemy 异步接口和 Alembic 建立表与索引；首版 SQLite 数据文件默认位于 Gateway 数据目录，`database_url` 可配置 PostgreSQL。迁移按实体分组，并提供空库初始化和已有库升级测试。
2. 先建立平台设置、用户/会话、设备/连接、项目/授权、供应商、用量、审计和作业所需的最小表；业务阶段再补字段和索引，避免一次性实现全部 repository。
3. Gateway 启动时校验迁移版本、数据库可用性和单实例约束；失败返回明确故障状态，不自动退回其他数据库。
4. 受管包配置固定 Gateway ID、地址和公钥 pin；daemon/desktop 读取并验证签名，不在普通设置页提供修改入口。受管配置与普通本地配置分离。

接口边界：数据库连接串只经部署配置传入；管理 API 只暴露后端类型、脱敏地址、健康与迁移版本。数据库后端切换必须离线备份/迁移，不在运行中热切换。

测试与验收：SQLite 冷启动、重复迁移、事务回滚、唯一约束通过；PostgreSQL 跑迁移和核心事务兼容测试；SQLite 锁竞争和慢盘下健康检查仍及时响应；配置损坏或签名不符时受管客户端拒绝连接，不破坏本地项目。

阶段 1 交付记录（2026-09-28）：实现分组 Alembic 迁移、异步数据库访问、SQLite 在线备份、SQLite/PostgreSQL 单实例约束、脱敏数据库状态摘要与受管包签名配置。迁移文件已确认进入 Gateway wheel；macOS 的受管桌面包已实际构建，成品中 Desktop 与随包 Python 均成功验签，Windows 打包留待发布阶段复核。Gateway/协议测试、daemon 生命周期和配置测试、Desktop 测试及构建脚本测试通过；PostgreSQL 17 临时容器的迁移与事务测试通过；SQLite 写锁和慢备份下健康检查及时响应。无管理登录前，数据库状态只保留在服务内部，阶段 2 之后再通过受权管理 API 暴露。回滚方式：撤销本阶段提交；阶段 0 的独立服务骨架仍可运行。

## 阶段 3A：Desktop 授权与设备注册

阶段 3A 进行中（2026-09-28）：Gateway 已实现短期单次 code、PKCE/state/nonce/网关与安装实例绑定、设备公钥登记及审批、停用/撤销、旧密钥证明后轮换、短期 Ed25519 设备授权；API/数据库与签名重启稳定性回归通过。Desktop 主进程已接入系统浏览器、协议回调、固定网关兑换和安全存储；Gateway Web 桌面登录页支持本地密码及第三方扫码回跳，`/admin/devices` 支持超级管理员二次认证后管理设备；daemon 已实现签名设备授权及私钥证明校验、本机会话和受管 HTTP/WebSocket 守卫。统一安装包目录、公开下载 API 与 `/devices/empty` 页面已实现，慢文件复制健康检查通过。本机会话失效专用标记、桌面端单飞重认证及受管请求 Origin 检查通过单元回归；实际安装包端到端验收尚未完成。

交付物：统一受管安装包可让当前用户登录并登记当前 PC。

开发顺序：

1. Desktop 生成 `state`、`nonce`、PKCE 和 `app_instance_id`，用系统浏览器打开固定 Gateway 的桌面登录入口；扩展现有 `workstep://` 路由处理 `auth/callback`，处理多开和重复回调。
2. Gateway 签发短期单次 authorization code；Desktop 用 PKCE 兑换用户与设备作用域会话。自定义协议 URL 仅包含 code 与 state。
3. PC 首次绑定生成设备密钥，Gateway 登记设备公钥、版本和绑定用户；管理侧可审批、停用、撤销与轮换设备身份。
4. daemon 建立 Gateway 派生的本机会话，将用户 ID、用户名及权限快照映射为统一当前操作者；本机 Web/API/业务 WebSocket 均要求该会话。
5. 登录成功后 Desktop 打开 loopback 工作台；下载页对所有用户提供同一网关受管包及校验信息。

测试与验收：code 过期、重放、错误 PKCE/state/app_instance_id 或错误网关均失败；登录后本机业务请求不经 Gateway 代理；无本机会话不能访问受管 API；关闭/最小化桌面窗口与完全退出 daemon 的设备状态区分准确。

## 阶段 3C：按需数据连接与整机远程代理

开发记录（2026-09-28）：已建立用户与整机分配管理、门户“我的电脑”列表，以及在线设备的短期签名访问票据和一次性子域兑换。按需数据 WSS 支持一次性握手、带流 ID 的 HTTP 分块和业务 WebSocket 双向转发；WS 消息按 16KiB 分块并限制总长度。远程 Web 有上下文提示，本机目录及桌面动作在远程降级。测试覆盖根路径、API、静态资源、流式大正文、双向 WS、撤权关流及慢数据连接时健康检查/控制心跳 canary。2026-10-03 已移除 Gateway 远程 HTTP/WebSocket 和 daemon 受管 HTTP 的请求 Origin 同源校验，继续依靠设备票据绑定、会话及项目授权；数据连接两端在握手确认支持后为 HTTP 与业务 WebSocket 启用每流 32 帧消费窗口，旧端继续使用原协议；PC 侧短请求结束后立即释放流名额。代理完整流控与容量、更多接口边界检查及受管包端到端验收仍待完成，阶段验收未通过。

交付物：用户在 Gateway 门户打开获整机授权的 PC，得到完整 WorkStep Web 界面。

开发顺序：

1. Gateway 校验 `user_devices` 整机访问关系，签发短期设备会话票据；浏览器经设备独立子域 `d-<opaque-device-id>.<gateway-domain>` 访问，部署提供通配符 DNS/TLS。
2. Gateway 经控制 WSS 通知 PC 建立按需数据 WSS；数据帧以 `stream_id` 多路复用 HTTP、业务 WebSocket、上传、下载、取消及流控。
3. PC 侧 ASGI bridge 把可信代理请求送入现有 FastAPI 应用，注入经过校验的当前操作者和设备作用域，不向本机 loopback 再发 HTTP。
