从一个项目，到可以使用的应用

2026-11-10 统一流程。用户说业务需求，系统完成技术选择；先预览，确认发布后才更新正式环境。

新添加的项目

添加项目 → 勾选作为应用 → 项目初始化 → 自动识别。

已存在的普通项目

项目设置 → 初始化为应用 → 进入同一套自动识别流程。

↓

1. 添加项目

用户：选择项目目录，按需要勾选“将这个项目作为应用”。

系统如何处理

沿用现有项目初始化；勾选后自动进入项目设置中的应用初始化面板。未勾选则保留普通项目，以后可以从项目设置继续。

↓

2. 自动识别项目

用户：通常不需要操作，只在多个应用或无法判断时补充。

系统如何处理

空目录：准备欢迎页和创建对话。已有代码：识别框架、Git、启动方式与 CI/CD。已有应用配置：恢复并验证，不重新套模板。Git 本身不代表已接入应用。

↓

3. 用业务对话说明需求

用户：告诉助手想解决什么问题、给谁使用、资料如何共享，以及喜欢的界面。

系统如何处理

应用创建 Skill 根据上下文逐个追问，自动选择技术模板、数据库和组件；已有应用优先保留原技术方案。

↓

4. 确认第一版要做什么

用户：查看功能、使用者、权限、界面和示例资料，选择“生成应用预览”或继续补充。

系统如何处理

记录业务需求与技术决策。欢迎页此时只是引导占位页，不冒充已运行的业务应用。

↓

5. 生成并启动草稿

用户：查看真实阶段进度；失败时可修正、重试或稍后继续。

系统如何处理

检查目录和冲突 → 准备隔离依赖 → 生成或适配代码和组件 → 准备测试库 → 验证启动 → 用真实预览替换欢迎页，并补齐项目流程和快捷按钮。

↓

6. 预览、操作与继续聊

用户：在应用窗口栏试用功能，在原对话中说哪里需要改。

系统如何处理

只修改草稿，正式应用继续运行。多个对话共享应用配置；并发写入需要协调。测试失败回到修改阶段。

↓

7. 发布给大家使用

用户：点击发布，查看本次变化、验证结果与必要风险，再确认。

系统如何处理

固定代码、提交与 Tag → 构建镜像 → 检查迁移风险 → 部署及健康检查 → 切换正式流量。创建版本不等于发布；失败必须显示代码和数据库的实际状态。

↓

8. 使用、分享与再次改进

用户：平时点“打开应用”直接使用正式版本；想改功能再打开对话。

系统如何处理

分享通过网关授权，绑定对应环境和实例；新的聊天修改继续进入草稿，不自动影响正式应用。

首次对话的样子

助手：你想做一个什么应用？可以说说现在遇到的麻烦。

用户：管理客户跟进，经常忘记联系客户。

助手：主要是你自己使用，还是公司同事一起用？

用户：五六个同事，主管可以看全部客户。

助手：我先做客户列表、跟进记录、联系提醒，并按负责人区分可查看的资料。先用示例资料生成预览，还是你想补充其他内容？

根据已有回答继续追问，不把框架、数据库和权限组件名称变成用户问卷。

日常使用与修改的布局

使用应用

项目列表 ｜ 应用窗口栏

无已打开对话时不创建聊天栏。正式应用顶部只保留名称、刷新、分享和收起。

聊天修改

项目列表 ｜ 当前对话 ｜ 应用窗口栏

有未发布变更时展示预览和发布能力。关闭对话仍保留变更状态。

每个应用都带业务 Agent

应用里提供“问助手”入口：了解应用、查询资料、操作业务，例如查找待联系客户、记录跟进、分配负责人。

业务聊天属于应用内部，打开后不增加 WorkStep 第四栏。使用者即使通过分享链接访问，也可按自身权限使用。

开发对话修改草稿代码；业务 Agent 调用当前环境的授权业务接口。正式 Agent 可以执行授权业务写入，但不能改代码或发布。新增功能同步提供业务说明和工具适配。

始终成立的规则

开发对话不写正式环境。草稿与正式数据库分开；兼容时复用测试库，不为每个 Tag 自动建库。正式数据复制先评估容量和耗时。数据库变更先做风险评估；代码回滚不等于数据恢复。关键边界由程序执行，不能只靠 Skill。
