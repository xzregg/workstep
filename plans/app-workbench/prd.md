# WorkStep 应用流程与产品需求

更新：2026-11-10。状态：设计规范，尚未实现产品能力。本文统一此前讨论；历史过程见 [归档](prd-history-2026-11-09.md)。[HTML 流程](application-flow.html) 与本文一致。旧交互原型中的技术表单不作为最新流程依据。

## 1. 产品模型

应用是项目的可选能力。用户把项目中的一个目录作为应用，由现有项目对话创建和修改功能，通过应用窗口栏使用和预览。

- 项目：保留现有项目身份、目录、对话、流程与设置。
- 应用配置：记录应用目录、框架、组件、运行方式、环境、部署和分享策略。
- 应用目录：项目根目录或子目录；版本操作以对应的实际 Git 仓库为边界。
- 草稿环境：可修改代码、独立依赖与配置、运行实例及测试数据库。
- 正式环境：运行已发布的固定构建产物，连接正式业务数据库。
- 应用版本：固定提交、不可移动 Git Tag、镜像 digest、schema／组件版本和验证记录。

用户界面统一称“应用”；第三栏名称为“应用窗口栏”，入口位于左侧项目列表的项目项右侧，文案“打开应用”。

## 2. 完整主流程

添加项目 → 完成现有项目初始化 → 自动识别应用 → 进入应用欢迎页与对话 → 用业务问题明确需求 → 确认首版方案 → 生成草稿 → 预览测试 → 发布 → 日常使用／分享 → 再次聊天修改。

应用初始化只有一套流程。添加项目时勾选应用，会在项目初始化完成后自动进入；普通项目可以稍后通过项目设置的“初始化为应用”接入同一流程。常规设置不平铺模板、框架、数据库和组件表单。

## 3. 添加项目与识别

### 3.1 添加项目

沿用现有添加项目流程，仅增加可选项“将这个项目作为应用”。选中后仍先完成项目注册与初始化；未选中时保持普通项目，不自动创建应用流程。

### 3.2 自动分析结果

| 项目状态 | 系统处理 | 用户需要做什么 |
| --- | --- | --- |
| 空目录／没有应用代码 | 选择默认应用目录，准备欢迎占位页面，匹配应用创建 Skill | 用业务语言描述要做什么 |
| 已有 Git 和代码，但没有应用配置 | 分析仓库边界、依赖、启动脚本、CI/CD、数据库与框架，生成接入提案 | 确认接入；只补充无法推断且实际阻塞的信息 |
| 已有可识别应用配置 | 恢复目录、版本、组件与环境配置，验证实际状态 | 打开应用或继续修改 |
| 多个可能的应用／无法识别 | 给出候选应用名称与目录提示，保留不确定状态 | 选择目标；必要时由技术人员展开高级配置 |

Git 仓库不等于已经接入的应用。分析只读，不运行安装和启动脚本。需要执行时明确实际目标和影响，复用现有权限与执行机制。

默认目录由系统选择：新空项目通常用根目录；已有项目优先识别已有应用目录。路径冲突或存在多个候选时再询问。不得静默创建嵌套 Git 仓库或覆盖已有代码。

## 4. 首次 Skill 引导

### 4.1 用户看到的界面

初始化进入应用欢迎页，并打开一段现有机制支持的新项目对话。三栏为“项目／对话列表｜当前对话｜应用窗口栏”。欢迎页属于平台引导占位页，不冒充已经生成并运行的业务应用。

首条消息：“你想做一个什么应用？可以说说现在遇到的麻烦。”

### 4.2 问题面向业务

| 要了解的事情 | 可以怎么问 | 系统据此决定 |
| --- | --- | --- |
| 核心用途 | 想解决什么问题？最先要完成哪件事？ | 首版功能、业务模板 |
| 使用者 | 自己使用、同事一起用，还是也给客户用？ | 登录、分享与运行需求 |
| 访问范围 | 谁可以查看或修改哪些资料？ | 账号与权限模型 |
| 现有资料 | 要导入已有表格，还是先用示例体验？ | 导入计划、测试数据 |
| 界面偏好 | 表格、卡片，还是让我决定？ | 页面结构与设计样式 |
| 实际规模／运行需求 | 仅在影响方案时问人数、数据规模、是否需要别人随时访问 | 数据库、部署及运行资源需求 |

问题按上下文逐个提出，允许自然语言、快捷选项和“帮我决定”。回答已有的信息不重复询问，不要求问完固定问卷。可以用样式预览帮助选择，不强迫用户识别设计系统名称。

默认不问 Node、React、ORM、SQLite、PostgreSQL、端口或 Git 等技术问题。技术方案自动记录，专业用户可在高级信息中查看或约束。需要外部服务、费用、数据外发或权限扩大时，用实际影响询问，不能隐含同意。

### 4.3 形成可确认的首版方案

对话生成业务摘要：做哪些功能、给谁使用、权限范围、界面示意和示例资料。用户可“生成应用预览”或继续补充。确认的是产品方案，而非技术参数清单。

已有应用以保留现有技术栈与功能为默认，只问想改什么；确实缺失的业务约束才追问。

## 5. 自动生成与可恢复执行

确认首版方案 → 生成技术配置 → 检查目录／仓库／文件冲突 → 准备独立依赖 → 生成代码与组件 → 准备草稿数据库 → 检查与启动 → 在 iframe 显示真实草稿页面。

执行进度使用实际事件，提供当前阶段、错误原因、日志和重试入口，不用计时动画伪造完成。失败保留已确认需求和有效产物，从可恢复位置继续。中断后可从同一项目继续，不重新提问全部需求。

准备工作补齐应用默认流程与快捷按钮：预览与测试、创建版本、发布、回滚、测试数据。重复执行不重复创建，不覆盖用户改过的流程。接入已有应用不生成新模板覆盖原文件，不重复触发原 CI/CD。

生成完成后对话继续：“预览已准备好，可以试着操作；想调整哪里，直接告诉我。”业务应用页面替换欢迎占位页，尚无正式版本时明确未发布。

## 6. 模板、Skill、组件与执行器

| 部分 | 职责 |
| --- | --- |
| 业务／代码模板 | 提供初始骨架、页面与默认配置，不要求非技术用户挑选具体技术框架 |
| 应用通用 Skill | 用业务问题引导需求，理解应用配置、草稿开发及版本规则 |
| 框架 Skill | 按实际框架处理代码、依赖、测试、数据库与迁移规范 |
| 组件 Skill 与模块 | 接入内置业务 Agent 聊天、登录、RBAC、统计等能力，声明接口与兼容版本 |
| 项目流程与执行器 | 实际执行启动、验证、构建、部署和回滚，记录结果并强制环境边界 |

新应用当前默认方向为 Node.js + TypeScript；前后端和数据库由模板结合业务需求自动选定。已有项目的 Python 等框架可以通过对应 Skill 接入，WorkStep 自身 daemon 架构不变。

技术选择及依据、Skill 版本、组件版本、运行时和依赖锁定信息持久化到应用配置／版本记录；后续任何对话沿用这些约定。不能只保存在一次聊天上下文里。

运行时优先复用检测到的受管理环境；Python venv／Node 依赖按应用隔离，不污染 daemon。桌面有独立 Python runtime，不代表具有可直接分发给业务应用的独立 Node CLI，必须检测兼容版本和缺失工具。

登录／权限／统计的业务需求由对话得出，前后端适配在草稿中完成并验证。权限必须在后端执行。网关访问认证与应用业务账号／RBAC 分开，通过显式身份映射接入，不能共享宿主私有数据库。

## 6.1 每个应用默认包含业务 Agent 聊天组件

业务 Agent 是应用使用界面的一部分，每个应用默认提供入口；分享或部署后仍可供有权限的业务使用者使用，不依赖打开 WorkStep 开发对话。用户可以通过它了解、查询和操作应用。

两类对话明确区分：

| 对话 | 目的 | 允许的操作 |
| --- | --- | --- |
| WorkStep 项目开发对话 | 创建和修改应用功能 | 修改草稿代码、测试、提出版本与发布操作 |
| 应用内业务 Agent | 理解和使用当前应用 | 按当前业务用户权限解释功能、查询数据、导航页面和执行业务操作 |

业务操作示例：“这个应用能做什么？”“找出本周还没联系的客户”“帮我记录一次跟进”“把这三条客户分配给王主管”。对话结果可以包含记录卡片、列表、图表、表单和可点击的页面入口。

组件接入契约：

- 应用能力说明：页面、业务术语、操作帮助、数据字段与规则，随应用版本维护。
- 业务工具清单：基于显式业务 API 定义参数、权限、读写性质、返回结构、确认规则和幂等策略。不能依靠任意 SQL、开发 shell 或无限制页面操控替代业务契约。
- 当前上下文：当前用户、角色、选中的业务对象、所在页面、环境及运行版本。回答使用实际查询结果；无权限、无数据或能力未接入时如实说明。
- 页面交互：需要导航、选中记录或填入表单时，由受控 UI 动作接口完成。iframe 与宿主间通信限定协议、实例和来源，不能开放通用脚本执行入口。
- 运行配置：模型调用由服务端认证和限额控制，不将密钥写进浏览器；未接通模型时明确显示尚未可用，不伪造可用聊天。

新模板同时生成基础 Agent 界面、说明和工具适配层。开发助手新增业务功能时同步更新 Agent 的能力说明和工具，并验证权限。已有项目接入时复用其业务接口，未适配的操作不出现在可执行工具清单中。

业务 Agent 的权限继承当前应用登录用户，每次工具调用仍由后端检查角色、对象归属和数据范围；分享访客不能因为进入聊天而提升权限。只读查询直接执行；需要确认的删除、批量更新、对外发送等操作先给出对象和影响范围，确认必须绑定实际参数与当前状态。失败、部分成功、取消和重试须真实可见，并记录操作审计。

草稿 Agent 连接测试数据；正式 Agent 可以按当前用户权限执行正式业务 API，因此“业务写入正式数据”是正常使用行为。它不具备改源码、迁移数据库或发布权限；开发与业务工具集、会话和环境上下文隔离。用户提出“加一个新功能”时，说明这是应用修改需求，仅有开发权限者才能显式交接到项目开发对话；不自动改动正式系统。

UI 在应用内部提供“问助手”入口，按需展开业务对话；这是 iframe 内的业务组件，不额外增加 WorkStep 第四栏。复用统一 Agent 会话、流式事件、停止、错误与工具调用基础设施，通过应用业务适配扩展；具体独立部署服务／SDK 方式待工程确定。

验收：应用可独立展示业务聊天；可解释当前版本实际能力、完成一项授权查询和业务写入；越权工具调用被后端拒绝；草稿不写正式库；正式业务聊天不修改源码；分享用户保持原权限；确认、取消、失败及幂等重试有可验证结果。

### 6.2 Agent 底层选型与供应商复用

应用内业务 Agent 属于平台统一基础组件，需要对运行框架、模型适配、工具调用、流式事件、会话存储和部署方式进行选型。不能每个应用自行生成一套聊天后端、重复填写供应商或复制密钥。组件、框架 Skill 和业务工具适配分别承担稳定基础设施、开发规范和应用业务能力。

应用默认引用 WorkStep 已配置且适合业务 Agent 的模型执行配置（供应商、模型、服务端点和能力约束）。平台已有多个可用配置时按平台／项目默认值选择；高级配置可覆盖。首次业务引导不要求用户理解供应商和模型名称。未配置、不可用或不具备所需工具调用能力时明确提示缺口，不静默改用未知供应商。

复用的是模型调用与认证适配能力，不自动继承开发 Agent 的 shell、文件、Git、发布工具或会话内容。业务 Agent 只挂载应用声明的业务工具，以应用当前用户权限执行。现有 CLI／SDK 引擎能否承载独立运行的业务 Agent 必须按实际能力评估，不能认为所有引擎均可直接嵌入网页。

应用配置保存供应商／模型执行配置的引用与业务工具声明，浏览器、模板、Git 和镜像中不包含供应商密钥。模型调用服务端解析凭据，审计记录应用、用户、运行环境、执行配置与用量。分享访客使用应用授权能力，不获得供应商配置管理权限。

本地托管时可经 WorkStep 受控模型服务调用既有配置。独立部署时明确选择经网关的应用级授权模型代理，或在目标服务器配置自己的模型服务；不能依赖开发机本地路径或将开发机凭据随应用打包。网关代理需具备应用鉴权、限额、撤销和故障反馈，这些属于待实现的能力，不宣称现有网关已支持。

具体 Agent 运行框架与默认模型代理方案仍待选型：优先验证现有基础设施能否复用，覆盖工具调用、取消、流式恢复、会话隔离与独立部署，再决定补充适配。模型供应商复用为确定方向，组件品牌和运行框架尚未确定。

## 7. 使用与修改的界面状态

| 状态 | 布局和内容 |
| --- | --- |
| 只打开应用，没有打开对话 | 项目列表＋应用窗口栏，加载正式应用；顶部为应用名、刷新、分享、收起 |
| 打开项目对话 | 列表＋当前对话＋应用窗口栏，保留原聊天组件；可以继续聊天和查看应用 |
| 已产生修改 | 明确提示未发布变更，显示草稿预览、正式应用及发布入口 |
| 关闭对话但仍有修改 | 隐藏聊天栏，保留未发布状态；不丢失代码、不自动发布 |
| 新应用尚未发布 | 使用欢迎／草稿状态，不将草稿标为正式应用 |

编辑时应用窗口栏按此前约定占桌面总宽度至少 70%。顶部按状态渐进展示；底部只有占满剩余空间的 iframe，无平台附加栏。日志、错误及执行细节通过对话或按需展开。

多个对话作用于同一项目应用，切对话不关闭应用。写代码须串行或隔离工作区后合并，不能互相覆盖。版本创建覆盖整个应用仓库的已纳入变更，不能误认为只包含当前对话。

手机暂沿用同一结构原型，展开三栏时横向查看；可用性、触控与键盘仍待真实设备验证，不视为已完成移动端设计。

## 8. 草稿、测试与数据库

开发对话、组件接入和升级只写草稿；草稿与正式的代码位置、依赖、配置、进程／容器、端口及数据库连接隔离。开发助手不得得到可直接用于业务写入的正式库凭据，环境边界由程序强制执行，不能依赖 Skill 提示。

数据处理规则：

- 不涉及 schema 变更时复用兼容测试库，不因聊天或创建 Tag 就重建数据库。
- 涉及 schema 变更时评估迁移当前测试库或创建隔离库，明确影响范围。
- 测试数据默认示例资料；需要时由用户选择导入／复制正式数据，不自动全量复制。
- 复制前评估体量、空间、耗时及脱敏需求，提供子集、仅结构、取消、重试和数据新鲜度信息。
- 版本固定代码与 schema 要求，环境绑定实际数据库实例；Tag 不等于数据快照。
- 历史版本在独立运行目录／固定镜像预览，使用兼容测试库，不切换正在编辑的代码目录。

测试失败返回草稿修改；涉及正式库的大表字段变更、锁、重写、额外空间与停机风险，需要基于证据评估，无法确定时显示未知，不能标为低风险。

## 9. 发布与回滚

用户看到：发布 → 查看本次变化、验证结果与实际风险 → 确认发布 → 查看结果。日常不要求理解 Git Tag 和 Docker。

后台顺序：固定变更范围 → 完成验证 → 固定提交和不可移动 Tag → 构建镜像一次并记录 digest → 发布前环境／数据库检查 → 必要迁移 → 候选实例启动与健康检查 → 切换正式路由。

创建版本可作为高级快捷操作独立触发；创建成功不等于已发布。构建失败保留失败状态，可对同一提交重试，不移动 Tag。部署复用同一构建产物。远程推送遵守仓库权限与配置，不隐含在本地 Tag 创建中。

失败时不切换正式路由，保留旧实例；若数据库迁移已经执行，必须展示其实际状态和恢复计划，不能宣称全部未改变。迁移要求尽量向前后版本兼容。

回滚先验证目标代码是否兼容当前数据库；兼容时切回旧镜像，保留现有业务数据。不兼容时禁止直接回退，进入独立的修复／数据恢复方案。代码回滚与备份恢复是两件事。

## 10. 分享与持续迭代

正式应用可以通过网关授权共享运行实例。分享链接绑定环境、实例和访问策略，可撤销；停止实例后不可访问。草稿分享需显式选择并告知内容会变化，不能默认替换正式分享。

后续循环：打开应用使用 → 打开对话提出改进 → 修改草稿 → 预览测试 → 发布 → 正式环境更新。全过程持续服务于同一项目身份。

## 11. 下一步验收与待定项
