# 业务域代码优化路线图

**状态：实施中（阶段一）。** 本计划基于 2026-09-25 的 `feat/codebase-optimization-20260925` worktree；实施时以最新代码和测试为准。阶段结果记录在文末，未记录的候选边界仍待核对。

## 目标与完成标准

让开发者或 AI 从 [`docs/code-map.md`](../docs/code-map.md) 找到功能所有者，能在一个明确的业务模块内修改状态、请求、校验和错误恢复。保留现有 API、WebSocket 事件、持久化格式、分享页能力及用户交互，除非某阶段明确要求改变。文件行数是发现混合职责的信号，**不是验收目标**；职责集中的大文件可以保留。

每一阶段完成时同时满足：

1. 为即将迁移的行为建立基线测试，先让新增的关键回归能发现遗漏，再移动职责；页面或路由测试只检查组装，行为测试跟随实际所有者。移动后删除依赖旧源码位置的断言，改为行为测试。
2. 新模块有清楚的接口和单一业务所有权，自己管理相关状态、请求、校验和恢复；不把整组 `state`/`setter` 或庞大的上下文对象从原文件透传。共用逻辑只在确实有多个调用方时上提。
3. 更新 Code Map、对应架构/开发文档和测试入口。Web 固定样式使用有语义的 class/id 与 CSS，运行时计算值才用 `style`；核对移动端控件尺寸及任务页/分享页一致性。
4. daemon 的同步文件、网络、SDK 和 Peewee 工作单元不得阻塞事件循环。涉及 I/O 的变更加入慢 I/O 或锁竞争 canary，验证健康检查或轻量协程仍响应。
5. 阶段相关测试、Web 全量测试与构建、daemon 全量测试及仓库检查通过；`git diff --check` 通过。记录确有价值的文件行数变化、剩余混合职责和无法拆分的理由，不以减行数冒充完成。

## 基线与实施方式

当前 `apps/web/src` 与 `apps/daemon` 中，排除测试和生成目录后，超过 800 行的业务源码共 **36 个：Web 13、daemon 23**。另外 4 个 i18n 词典超过 800 行，主要由文案构成，不进入拆分清单；新增文案仍须保持各语言键集合一致。任务详情 View 已从 3466 行降到 2255 行，但对话区域仍是下一条重要边界。

按下面阶段顺序推进，每个阶段可分成若干小提交。开始一个阶段前先对照最新 `main` 与优化 worktree，更新基线和受影响测试；在现有优化 worktree 中实施，保持主工作区不受影响。同一文件不要在多个阶段并行编辑。若分析发现候选边界会增加维护入口或破坏局部性，应在阶段记录中说明并保留原位。

**验证重点：** 各引擎能力矩阵、事件声明与产出一致、审批/停止/恢复/分叉、超长 JSONL 和同步 SDK 慢调用隔离；运行现有引擎契约测试。
